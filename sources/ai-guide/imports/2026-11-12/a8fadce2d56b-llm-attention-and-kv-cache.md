哈喽大家好，我是欧呦，这篇文章将为大家分享大模型的底层运行原理——不推数学公式，直接把平时经常听到的 Token、注意力机制（Attention）和 KV Cache 讲明白。

很多朋友在使用 AI Agent 或者普通 AI 对话的时候，经常会遇到几个让人困惑的现象：

为什么在同一个聊天窗口里聊得越久，AI 就越容易忘掉最开始定好的要求、改代码的质量也越来越差？为什么大家经常在说「要用 Skill 按需加载」「要用子 Agent 隔离上下文」「不要随便改动系统提示词的开头」？

其实这些现象和使用习惯，背后全都由大模型的两个底层机制决定：一个是 **注意力机制** ，另一个是 **KV Cache（键值缓存）** 。把这两个概念搞懂，我们以后不管是用 AI Agent 写代码，还是自己设计 AI 产品，心里都会更加清楚它背后的工作机制。

## 大模型是怎么生成回答的

在聊注意力机制和缓存之前，我们先花两分钟，把「我们在输入框里发出一句话，到大模型给出回答」这中间最基础的三件事理清楚。

### 1\. 模型眼里没有整句话，只有切分开的词块（Token）

当我们把一段中文、英文或者代码发给大模型时，模型并不是像人眼一样直接按字阅读的，它会先把这段话切分成一小块一小块的文本片段，每一小块就叫一个 **Token（词块）** 。

一个 Token 可能是一个常见的英文单词、半个长单词，或者一两个汉字。模型读入内容、计算上下文关系、生成回答，全都是以 Token 为最小单位来进行的；平时我们说的「上下文窗口有 200K」「这轮消耗了多少额度」，指的也是 Token 的数量。

### 2\. 大模型本身是「没有记忆」的（无状态）

平时我们在聊天窗口里跟 AI 一来一回聊了十几个回合，感觉它好像一直记着我们刚才说过的话。但实际上， **大模型本身是完全「无状态（Stateless）」的** ——它每回答完一句话，自身并不会保留任何对话状态，也不记得上一轮发生过什么。

那为什么第 10 轮对话时，它还能接上第 1 轮提的需求？

原因在于我们使用的客户端软件（比如网页聊天端或桌面端 AI Agent）在背后帮我们做了拼接：当我们发送第 10 轮的那句话时，客户端会把 **第 1 轮到第 9 轮聊过的所有对话、AI 读取过的所有文件内容、工具返回的执行日志，再加上刚输入的第 10 句话，拼成一份完整的长文本，从头到尾重新发给大模型** 。

所以，在同一个窗口里聊的轮次越多，每次发给模型的文本内容就越庞大。

### 3\. 回答不是一次性想好的，而是「一个词一个词往后预测」

很多人以为大模型收到问题后，是先把整篇回答想好，再像打字机一样展示出来。其实不是。

大模型生成回答的方式叫做 **自回归生成** ，也就是 **逐词往后预测** 。它每次只做一件事情： **根据前面已经出现的所有 Token，计算并预测「下一个位置最应该出现什么 Token」** 。

比如我们问它「法国的首都是哪里」，它读完问题后先计算一次，预测出第 1 个字是「巴」；接着它把「巴」字拼到原问题的末尾，变成「法国的首都是哪里 巴」，再拿这整串内容去预测下一个字是「黎」。像这样每预测出一个词块，就把它追加到末尾作为新的前文，一步步循环往后生成，直到输出代表回答结束的标记为止。

## 注意力机制与长上下文衰减

既然大模型是通过「阅读前文、预测下一个词」来工作的，那当它面对前面成千上万个词块时，它是怎么搞清楚上下文里的指代关系和重点信息的？靠的就是 **注意力机制（Self-Attention，自注意力机制）** 。

### 1\. 用一句话看懂注意力机制在干什么

我们来看这样一句话：

- 「小狗跑得气喘吁吁也没追上那只猫，因为 **它** 实在太累了。」

我们一眼就能看出来，这句话里的「它」指的是前面跑得气喘吁吁的小狗，而不是猫。但对于从左往右处理文本的大模型来说，「它」和「累」跟前面的「小狗」中间隔了好几个词，模型是怎么知道「它」指代谁的呢？

当模型从左往右读到「它」和后面的「太累了」时，注意力机制就会带着当前词的上下文线索， **回头去比对前面的每一个词块** ，计算当前词与前面各个词之间的关联程度。模型经过计算，发现前面「跑得气喘吁吁」的「小狗」关联度最高，而跟「没」「那只」这些词几乎没有关联——于是模型就会把主要权重分配给「小狗」，从而准确理解这里的语义。

### 2\. 拆解 Query、Key 和 Value 的作用

如果我们去看讲解大模型原理的资料，经常会看到 **`Q（Query）` 、 `K（Key）` 、 `V（Value）`** 这三个概念。它们其实是模型在处理每一个词块（Token）时，为该词块计算出来的三组不同特征：

1. **Query（查询需求 · 我需要寻找什么信息）** ：代表当前正在处理的这个词块，想去前文里寻找什么样的关联线索。比如模型读到「它」或「累」时，它的 `Query` 就是在寻找「前面发出了奔跑动作的主语」。
2. **Key（特征标签 · 我包含什么属性）** ：排在前面的每一个词块，都会有一个结合前文语境算出来的特征标签，用来说明自己是什么角色。比如前面的「小狗」，它的 `Key` 就标识出自己是「名词、动物、句子前半段的主语」。
3. **Value（实际内容 · 我能提供什么语义）** ：代表这个词块本身携带的具体语义信息。

当模型要理解当前词块时，就会拿当前词的 **`Query（查询需求）`** ，去和前面所有词块的 **`Key（特征标签）`** 逐一计算匹配分数；谁的匹配分数高，就会分配到更高比例的注意力权重，最后按这个权重比例，把前面各个词块的 **`Value（实际内容）`** 聚合起来。

### 3\. 为什么同一个窗口聊久了，AI 容易漏掉要求？

理解了「逐一比对打分、按比例分配权重」的过程，我们就能明白为什么同一个聊天窗口里的内容太多时，AI 容易忘掉要求或改错代码了。

核心原因在于： **模型每预测一步，分配给前面所有词块的注意力权重总和是固定的（加起来等于 100%）。**

当对话刚开始、窗口里只有一两千字时，我们交代的核心需求、代码规范和边界条件非常集中，能够分到很高的注意力权重。

但如果在同一个窗口里连续聊了很久，或者让 AI Agent 读取了几十个源码文件、塞进了大量终端报错日志，上下文就会膨胀到几万甚至十几万个 Token。这时候，模型每生成下一个词，都要拿当前的 `Query` 去和前面几万个词块的 `Key` 逐一计算。

原本集中投向核心指令的注意力权重，就会被大量已经过时的旧日志和无关代码片段分散稀释。最开始交代的那几句关键要求，分到的权重比例会大幅下降——这就是为什么哪怕模型的上下文窗口上限标着 200K 甚至 1M，只要塞进过多无关信息，它的实际表现依然会明显下降。

## KV Cache 与提示词缓存

看完注意力机制的计算过程，我们会发现一个很明显的计算效率问题。

前面我们讲过：大模型是「一个词一个词往后预测」的，而且每预测一个词，都要拿当前词的 `Query` 去和前面所有词的 `Key` 与 `Value` 做比对。

假设我们发给大模型一篇 1 万字的文档，让它写一段 200 字的总结：

- 它生成第 1 个字时，需要把前面 1 万个字的 `Key` 和 `Value` 全部计算一遍；
- 紧接着它要生成第 2 个字了。这时候，前面那 1 万个字没有任何变化，如果模型每次都把那 1 万个字的 `Key` 和 `Value` 从头到尾重新计算一遍，那么生成 200 个字，就等于把这 1 万字的内容重复计算了 200 遍。

如果真这么做，生成到后面就会越来越慢，大量算力都会消耗在重复计算上。

### 1\. KV Cache（键值缓存）：把算过的中间结果存进显存复用

为了避免这种重复计算，大模型利用了一个关键特性： **模型处理文本是从前往后单向进行的** 。

也就是说，第 100 个词算出来的 `Key` 和 `Value` 本身融合了前 99 个词的语境，但后面新生成的第 101 个词，不会反过来改变前面 100 个词已经算好的 `Key` 和 `Value` 。

既然前面词块的 `Key` 和 `Value` 不会再变化，模型每算完一个词，就会把它的 **`K` 和 `V` 直接保存在显卡显存里** ——这部分保存在显存里的中间计算结果，就叫做 **`KV Cache（键值缓存）`** 。

有了 `KV Cache` 之后，当模型生成第 101 个字时，前面已经算过的部分直接从显存里读取即可，只需要计算最新这 1 个字自己的 `Q、K、V` 。这也是为什么我们使用 AI 时，刚按下回车等待第一个字出现会有一小段停顿（这时模型正在集中计算输入文本的 `KV Cache` ，称为 **预填充 Prefill** ），而一旦第一个字出现后，后面的文字就能很快地连续生成出来（称为 **解码生成 Decode** ）。

### 2\. 从单次生成到跨请求复用：什么是「提示词缓存（Prompt Caching）」？

早期的 `KV Cache` 只在单次回答的过程中生效，回答结束后就会释放。但在使用 AI Agent 时，情况有所不同。

当我们用 AI Agent 写代码或处理任务时，交代一个需求后，Agent 往往会在后台连续调用二三十次工具（读取文件、搜索代码、修改文件、运行测试）。因为大模型本身是无状态的，所以 Agent 每调用完一次工具，都需要把 **「系统提示词 + 工具定义列表 + 项目规则文件 + 之前的对话和工具记录 + 最新一步的执行结果」** 重新拼成一次完整请求发给模型。

可以看到，在连续几十次请求里，前面绝大部分文本内容都是完全一致的，只是在末尾追加了最新一步的结果。

为了避免每次请求都把前面几万字相同的内容重新计算一遍，OpenAI、Anthropic、DeepSeek 等厂商都支持了跨请求的 **提示词缓存（Prompt Caching）** ：

服务器计算完当前请求的 `KV Cache` 后，会在缓存中保留一段时间。当我们紧接着发出下一次请求时，只要前面那一段内容与上一次完全一致，服务器就会直接复用已有的 `KV Cache` —— **命中的这部分内容不仅省去了重复计算的时间、让响应更快，而且各家厂商通常会对命中缓存的 Token 提供约 1 折的计费优惠（节省约 90% 的输入成本）** 。

### 3\. 为什么「改动开头的内容，后面的缓存就会全部失效」？

这也是在配置提示词或开发 Agent 工具时需要注意的一点： **提示词缓存必须满足严格的「精确前缀匹配（Exact Prefix Match）」** 。

比如在系统提示词的最开头放了一句每秒变化的动态时间戳（如 `当前时间：2026-10-30 14:20:05` ），那么每次发起请求时，因为开头的文字变了，后面哪怕跟着几万字完全相同的代码和文档，缓存也无法命中。

结合前面的原理，原因其实很容易理解：

因为大模型是从前往后依次计算的， **后面每一个词块算出来的 `KV Cache` ，都依赖于排在它前面所有词块的完整内容** 。一旦排在最前面的某个词发生了变化，从这个位置往后的所有词块，它们对应的前文语境就全都变了，之前保存的 `KV Cache` 就无法继续复用，只能从发生改动的位置开始重新计算。

## 结合底层原理用好 Agent

理解了「注意力权重会被过多无关内容稀释」和「KV Cache 依赖从前往后的前缀一致」这两个机制后，再看平时使用 AI Agent 的几项常见操作，就能很清楚它们各自解决的是什么问题：

### 1\. 用 Skill 做「按需渐进式加载」，不要把所有规范都塞进全局规则文件

如果我们把几万字的 UI 规范、文案规范、发布流程全部写进每次对话默认加载的 `AGENTS.md` 或 `CLAUDE.md` 里，哪怕当前只是修改一行简单的代码，这些暂时用不上的长文档也会一直占用上下文、分散模型的注意力权重。

把专项知识拆分成独立的 Skill（详见 [《从 0 到 1 了解什么是 Skill》](https://book.oiloil.org/articles/skill-guide) ），平时只加载简短的名称与触发描述，真正需要执行对应任务时再去读取详细文件，就能让上下文始终保持精简。

### 2\. 会产生大量中间过程信息的任务，交给「子 Agent」在独立上下文中执行

像「在几十个文件里检索某段逻辑」「排查几千行的报错日志」这类任务，执行过程中需要读取大量文本，但最终有用的往往只是几句话的结论。

如果全部在主对话窗口里执行，这些中间读取的文件和日志都会留在主窗口的历史记录里，后续每一轮对话都会继续占用注意力权重并消耗 Token。将这类探索或检查任务交给子 Agent 在独立窗口中完成，只把最终结论返回给主 Agent（详见 [《怎样用好子 Agent》](https://book.oiloil.org/articles/subagent-workflow) ），就能保持主对话上下文的干净。

![将产生大量中间信息的探索与排查任务交给子 Agent 隔离执行](https://book.oiloil.org/assets/articles/llm-attention-and-kv-cache/04b-subagent-isolated-context-v1.svg)

将产生大量中间信息的探索与排查任务交给子 Agent 隔离执行

### 3\. 完成一个独立任务后及时新开对话，或用 /compact 压缩历史

尽量不要在一个聊天窗口里连续处理多个毫不相干的任务。当一个功能模块已经开发完成，或者上一阶段的报错已经解决后，前面几十轮的调试过程对下一个新任务来说就会变成无关的干扰信息。

这时直接新开一个对话窗口（或者在长任务中途使用 `/compact` 将冗长的工具调用历史压缩为简短摘要），可以让模型的注意力重新集中在当前任务上，也避免每次发消息都重复携带大量历史记录。虽然执行 `/compact` 压缩历史的那一次请求会重新生成新的前缀缓存，但相比后续每一轮都带着几万字的无用记录，整体算下来依然更高效、更省额度。

![完成独立任务后及时新开对话或使用 /compact 压缩历史上下文](https://book.oiloil.org/assets/articles/llm-attention-and-kv-cache/04c-new-topic-and-compact-v1.svg)

### 4\. 固定内容放在开头，动态变化的内容追加在末尾

无论是整理项目的规则文档，还是自己开发 Agent 应用，都可以顺应 `KV Cache` 的前缀匹配机制来安排内容顺序：

- 把固定不变的系统指令、工具列表和通用项目规范放在最前面，在连续对话中途尽量不要频繁增删工具或修改前面的内容；
- 像动态状态、补充说明或新一轮的工具返回结果，统一往消息列表的 **末尾** 追加。

只要保持前面的长前缀稳定不变，AI Agent 在多轮连续执行时就能持续命中 `KV Cache` ，既能减少等待时间，也能显著降低 Token 消耗。
