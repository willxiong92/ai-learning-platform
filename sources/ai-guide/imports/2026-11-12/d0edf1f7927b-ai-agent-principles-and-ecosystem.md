## 前言

哈喽大家好，我是欧呦。很多刚开始接触 Vibe Coding 或者刚开始使用 AI Agent 的朋友，平时应该经常听到各种技术概念——比如说提示词（ `Prompt` ）、上下文工程（ `Context Engineering` ）、 `MCP` 、 `CLI` 、 `Skill` 或者是 `Harness` 。

大家在听到这些词的时候，可能经常会觉得疑惑： **因为它们里面有些东西的功能是重叠的，或者说是相互包含的。** 比如既然 `MCP` 已经能够帮助 AI 去连接外部工具了，为什么现在大家还需要去使用 `Skill` 加 `CLI` 的方式？它们之间到底是怎么配合的？

在这篇文章里，我就结合从 ChatGPT 诞生以来我自己的实际使用和开发经历，顺着时间线，把每个时期出现的名词以及它背后的技术逻辑串起来讲清楚：

## 一、Prompt 与 Context：从写提示词到理解上下文

### 1\. 提示词（Prompt）的三种写法与局限

我们把时间拨回到 **2022 年 11 月 30 日** ，这一天 OpenAI 发布了 **ChatGPT** 。ChatGPT 诞生之后，第一个走入大家视野的概念就是 **`Prompt` （提示词）** 。

![早期 ChatGPT 时代通过设定角色、给参考例子与一步步思考编写 Prompt 及无法直接执行操作的局限](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/10-early-prompt-engineering-v1.svg)

早期 ChatGPT 时代通过设定角色、给参考例子与一步步思考编写 Prompt 及无法直接执行操作的局限

在当时那个阶段，大模型只能跟我们纯文字对话，没有任何操作外部软件的能力。所以我们能够去介入 AI 执行过程的唯一手段，就只有修改发给它的提示词。

因为当时面对同一个模型，我们随口问它一句，和精心组织语言去问它，得到的回答质量差别很大，所以全网很快掀起了研究 **「提示词工程（Prompt Engineering）」** 的热潮，大家都在琢磨怎么把提示词写好、让 AI 给出更好的回答。

当时大家是怎么写提示词的呢？最核心的写法主要有三种：

- **第一，分成系统提示词（ `System Prompt` ）和用户提示词（ `User Prompt` ）** ： 系统提示词就是给 AI 一个背景人设与规则要求——比如「你是一个有 10 年经验的资深程序员，请用最直白的语言回答，代码必须加上中文注释」；而用户提示词就是跟在后面的具体问题。告诉它「你是程序员」之后，接下来我就问它代码相关的问题；如果我想问英语相关的问题，给它的系统提示词就换成「你是一个英语老师」（2023 年 3 月 OpenAI 开放 API 时，正式在接口层把 `System Prompt` 和 `User Prompt` 拆成了两个独立字段）。
- **第二，给一些参考例子让模型去模仿（ `Few-shot` 少样本提示）** ： 如果光讲要求 AI 还是理解不准，就在提示词里给它列 2～3 个「输入是什么 → 理想输出是什么样」的真实示例。因为大模型非常擅长找规律，看完例子之后，就能很好地按照你预期的格式输出结果。
- **第三，要求它「一步步思考」（ `CoT` ，Chain of Thought 思维链）** ： 现在我们用的很多模型都自带思考（ `Thinking` ）流程，但以前的模型是没有的。当时大家发现，在做数学题或复杂逻辑题时，如果要求它「先把中间的解题过程自己推理一下，不要直接给我最终答案」，准确率就会大幅提升——比如 2022 年 5 月东京大学与 Google 团队在论文《 *Large Language Models are Zero-Shot Reasoners* 》中发现，哪怕一个参考例子都不给，只要在提问末尾加上一句 `"Let's think step by step"` （让我们一步步思考），当时 GPT-3 在数学应用题测试集（MultiArith）上的准确率就直接从 `17.7%` 暴涨到了 `78.7%` 。当时这一步是靠我们在提示词里手动引导它去做的，到了后来，厂商就把这一步直接内化到模型本身里面去了。

不过到了后来，大家也慢慢发现了单靠写提示词有两个非常明显的局限：

1. **提示词本身的作用是有限的** ：不同模型的编程能力差别很大，你不可能跟一个基础能力很弱的模型说一句「你是一个 10 年经验的资深程序员」，它的编程能力就能突飞猛进，这是不可能的；
2. **它只能响应文本，没有办法去执行具体的工作** ：当时我们只能单纯跟它对话，AI 接收到提示词之后只能回复我们一段文字。比如我们让它写了一段代码，大多数时候还得由我们自己手动把代码复制出来，再粘贴到编辑器里去运行。

### 2\. 什么是 Context（上下文）？

在看 AI 怎么突破「只能回复文字」的局限之前，我们先顺手把另一个跟 `Prompt` 紧密相连的基础概念—— **`Context` （上下文）** 理清楚，因为后面所有的工具调用和工程演进都围绕着它展开。

**首先， `Prompt` 其实是 `Context` 的一部分** ——上下文就是我们跟 AI 对话里面包含的所有信息；假设除了提问之外，我们又给 AI 塞了一些其他的背景资料或文件内容进去，那么这些资料也属于上下文（ `Context` ）的一部分，但它们不属于你写的提示词（ `Prompt` ）。

![Prompt 单次指令与 Context 完整记忆窗口的构成及精简原则](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/02-prompt-vs-context-anatomy-v1.svg)

Prompt 单次指令与 Context 完整记忆窗口的构成及精简原则

要真正理解 `Context` （上下文），我们首先要知道大模型的底层特性： **模型本身是「无状态（Stateless）」的。**

什么叫「无状态」呢？就是我们跟它对话的这些历史信息，并不是模型自己脑子里记住了，而是在下一次问它问题之前，聊天软件把之前所有聊过的信息都重新再发给它了一遍。

举个最简单的例子：

- 我先跟它发一句：「你好」；
- 它回复我：「我是 ChatGPT」；
- 紧接着下一句我问它：「我忘记你叫什么名字了」。

它在下一句之所以能回答出自己叫「ChatGPT」，其实是因为软件把前面的对话连同我最新的这个问题 **一起打包发送给了它** ，它基于前面这几句话再去推理出新的回答。如果我们单独只把「我忘记你叫什么名字了」这几个字发过去，模型是根本回答不出来的。

**我们每一次对话时打包发给大模型的全部内容，就称它为 `Context` （上下文）。**

上下文有一个贯穿至今的核心规律： **上下文并不是塞得越多越好，而是越精简、越干净，AI 执行的效果就越好。** 主要原因有两个：

1. **`Token` 有容量上限（最大上下文窗口），塞满了就没法继续聊了** ： 我们在跟 AI 对话时，文字是按 **`Token`** 来算容量和计费的（大约 1 个英文单词或 1 个常用汉字算 1～2 个 Token），每个模型都有一个最大的上下文窗口上限。 假设我只是想问你「今天天气是什么」，结果在最开始给你塞了一大堆写代码相关的东西——这些内容对于回答今天天气没有任何帮助，应该给的是天气相关的信息。而且因为每次对话都要把历史记录重发一遍，当无关的历史信息塞到一定程度、把窗口撑满之后，就没法再跟它继续对话了。
2. **历史信息太长，会严重分散模型的注意力** ： 这里我们不详细展开模型底层的注意力机制（感兴趣的朋友可以看 [《大模型的注意力机制与 KV Cache》](https://book.oiloil.org/articles/llm-attention-and-kv-cache) ），大家只需要知道一个结论： **在跟模型对话时，你的上下文越长，模型去召回（找到）之前相关内容的难度就越高** 。斯坦福大学等团队在 2023 年 7 月发表的《 *Lost in the Middle* （迷失在中间）》实验也印证了这一点：当窗口里塞入几万字无关内容时，模型对夹在中间的关键要求识别准确率会暴跌 `20%–30%` 以上。你不给它塞任何杂乱的东西，直接问它天气是什么，它反而回答得更好。

所以说，我们平时常听到的 **「上下文工程（Context Engineering）」** ，很多时候就是在研究： **在程序上，我们怎么给 AI 模型提供越精简、越干净的上下文。**

## 二、学会动手与思考：Tool、ReAct 循环与推理模型

### 1\. 工具调用（Function Calling / Tool）的原理

前面我们提到，最早的 AI 是没有办法去执行具体任务的，它只能用文字回答问题。但我们希望大模型不只能回复文字，还能够真正帮我们干活。

于是 OpenAI 在 **2023 年 6 月** 的 API 更新里，新增了一项叫 **`Function Calling` （函数调用）** 的技术，后来在 2023 年底统称为 **`Tools` （工具调用）** ，Anthropic 的 Claude 等模型后续也支持了类似的能力。

![大模型与本地 Agent 软件通过结构化 Tool 调用卡完成本地操作的四步流程图](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/03-tool-execution-loop-v1.svg)

大模型与本地 Agent 软件通过结构化 Tool 调用卡完成本地操作的四步流程图

很多朋友可能会好奇： **大模型从原理上来讲只能收发文字，那它是怎么样去读取或者修改我们电脑里的文件、怎样去调用工具的呢？**

我们可以对照上面的流程图来看。 `Function Calling / Tool` 的原理其实是这样的：

1. **发请求时带上可用工具** ：当本地软件给云端 AI 发送请求时，会顺带告诉它有哪些工具可以用——比如「我给你提供一个读文件的工具（ `Read` ），以及一个写文件的工具（ `Edit` ）」；
2. **模型返回固定格式的 `JSON` 字符串** ：当我让 AI 去读本地的 `index.html` 文件时，模型调用工具的方式，是 **写一串带固定格式的 `JSON` 字符串（一种方便程序直接识别的「字段名: 值」标准文本格式）返回给我** ：
	```
	{ "tool": "Read", "path": "index.html" }
	```
	也就是说， **本质上云端大模型还是在回复我一串文本，只不过这串文本是有严格格式的** （它告诉我们 `tool` 是 `Read` ，文件路径 `path` 是 `index.html` ）；
3. **本地软件执行程序并把结果塞回上下文** ：我电脑上的本地客户端软件一识别到这段格式，就会在本地执行读取文件的程序，打开 `index.html` 读出里面的代码；随后，本地软件再通过程序把读到的代码内容重新塞进大模型的 `Context` （上下文）里，发回给云端大模型。

这样一来，云端模型就相当于在本地读到了我们的代码。 **云端大模型自始至终都没有直接操作我们的电脑，真正执行文件读写的，是我们电脑上的客户端软件。**

### 2\. 从单次调用到 ReAct 自动循环

上面这套工具调用的逻辑跑通之后，我们今天所用的 **AI Agent（智能体）** 的基础形态就正式诞生了，它具备了执行工具调用的能力。

**但是在这个阶段，它还缺少一个什么关键能力呢？就是假设刚才那个文件读取失败了怎么办？**

![普通聊天 AI 的单次一问一答与 AI Agent 自动循环及模型解耦的对比](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/01-chat-vs-agent-loop-v1.svg)

普通聊天 AI 的单次一问一答与 AI Agent 自动循环及模型解耦的对比

假设我让 AI 去读 `index.html` ，如果读失败了，本地程序就会告诉它「文件读取失败」。但如果此时的 AI 还是纯对话模式的，它不会因为你告诉它读取失败了，就自己基于这个失败结果再给你一个新的读取命令——它直接就停下来不工作了。

为了解决这个问题，行业里引入了一个核心机制，叫做 **`ReAct`** 。

注意，这个 `ReAct` 不是前端开发的那个 React 框架，它是 **`Reason` （推理）+ `Act` （行动）** 两个词拼在一起的缩写（这个机制的研究者姚顺雨大家现在应该很熟悉了，他当时在 Google 发表了这篇论文，目前在腾讯负责混元大模型的研发）。

`ReAct` 的核心意思就是让 AI 形成一个「思考与行动」的闭环：

- **先思考下一步要干嘛（ `Reason` ）** ；
- **再调用一下工具（ `Act` ）** ；
- **接着去观察工具返回的结果（ `Observation` ），并根据这个结果思考下一步怎么行动** 。

还拿刚才读取文件的例子来说：

- 如果 `index.html` **读取成功了** ，AI 就根据读出来的文件内容执行下一步操作（比如照着你的要求去修改代码）；
- 如果 **读取失败了** ，AI 就会回头去看一下自己刚才写的命令——假设是文件路径写错了，或者调用的工具名字写错了，它就会修改一下参数，再重新发出下一步工具调用。

因为每一次调用工具之后，本地程序都会给 AI 一个结果反馈，让它评估这一步做成了没有， **这样我们就实现了一个自动运转的循环（ `Loop` ）：AI 可以一轮接一轮地去读文件、改代码、跑测试、看报错再修改，直到任务彻底完成。**

而且理解了这一点，大家就会明白一个很重要的共识： **这个 `ReAct` 循环是在我们电脑本地的 AI Agent 软件程序里执行的，而它的「脑子」（云端大模型）是可以随时切换、互不绑定的** ——比如你在同一个 AI Agent 软件里，随时可以把底层模型从 Claude 切换成 GPT 或 DeepSeek，外层的循环和工具依然照常工作。

### 3\. 从固定工作流（Workflow）到推理模型（Thinking）

这里还有一个前两年大家经常听到的概念，叫做 **`Workflow` （工作流）** ——比如当时很多人用 n8n、扣子（Coze）、Dify 去画那种固定流程图（最近扣子部分服务也下线调整了，现在大家用固定 Workflow 比以前少了很多）。

**既然前面已经有了 `ReAct` 循环，为什么在 2023 到 2024 年会出现 `Workflow` 这种画固定流程图的机制呢？**

![2024 年人工连线的固定流程图工作流与 2025 年推理模型驱动的自主循环对比](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/11-workflow-vs-reasoning-loop-v1.svg)

2024 年人工连线的固定流程图工作流与 2025 年推理模型驱动的自主循环对比

原因在于： **早期的模型本身没有深层的推理和反思能力，能力还不够强。**

在 2023 年底，普林斯顿大学发布了检验 AI 解决真实 GitHub 项目 Bug 的基准测试 **`SWE-bench`** ，结果当时基于早期 GPT-4 的 Agent 真实问题解决率只有 **`1.96%`** 。当时如果完全依靠模型自己在 `ReAct` 循环里自由分析下一步要做什么，一旦它第一步做错了、或者工具报错了，哪怕你给了它报错反馈，它也反应不过来下一步该怎么调整， **只会在那里一直重复犯错、自己卡死** ，根本没办法像我们现在的 AI Agent 这样自己连续干十几个小时。

为了弥补当时模型能力的不足，大家就不敢让它那么灵活自由地自己规划任务，而是给它把执行流程固定死——这就是 **`Workflow` （固定工作流）** 。

我们可以用一个简单的例子来理解 `Workflow` ：假设我想拿一段视频做一张小红书的封面图，我希望它的流程是固定的三步：

1. **第 1 步** ：先在视频里面找到适合放在封面上、有清晰屏幕展示的一帧画面；
2. **第 2 步** ：针对视频字幕去想一个切合视频主题的标题；
3. **第 3 步** ：调用生图工具，把这张封面图片生成出来。

这三步是一个非常固定的流程，在当时用 `Workflow` 就能让它跑得很稳定。

**而且要注意， `Workflow` 和我们现在在 `Skill` 里面写一个流程还不一样** ：

- 我们现在写一段提示词或者写一个 `Skill` 告诉 AI 流程怎么走， **本质上还是 AI Agent 看了这段文字之后，自己去规划任务怎么执行** ；
- 而之前的 `Workflow` 是 **通过程序的方式去硬性限制它的** ——比如第 1 步「在视频里抽帧」，可能根本不是 AI 去做的，而是本地程序强制先跑一段抽帧代码；AI 在整个环节里只是看了一下视频或字幕、输出一个结果，整条流水线其实是把多次独立的 AI 单次调用拼在一起组成的（关于固定工作流与自主 Agent 的适用边界，推荐延伸阅读站内精选收录的 Anthropic 团队名篇 [《构建有效的 AI Agent》](https://book.oiloil.org/articles/building-effective-agents) ）。

**那么，为什么到了 2025 年之后，大家又不需要画死板的流程图，AI Agent 自己就能稳稳跑完复杂循环了呢？**

因为 **2024 年底到 2025 年初** ，行业推出了非常重磅的、带有原生思考链的推理模型——代表就是 **OpenAI 的 o1** 以及 **DeepSeek 的 R1** （到现在，我们基本上已经见不到没有 `Thinking` 能力的模型了，几乎全部都是带思考的模型）。

以前的模型是你给它发一句话，它直接就一个字一个字地往外吐答案 Token；而从 DeepSeek-R1 这类推理模型开始，你会发现它在回答前会先在思考区（ `Thinking` ）里「噼里啪啦」自己推理一大通：「我猜测用户是什么意思、刚才报错是因为什么、我下一步应该先查哪个文件……」，先在内部进行一波深度推理，然后再给出最终结论或调用工具——配合现代工具链后，AI Agent 在同一个 **`SWE-bench Verified`** 测试上的解决率直接从早期的 `1.96%` 跃升到了 **`70%–80%` 以上** 。

**为什么多出这一步「思考（Thinking）」，就能大幅提升它调用工具和回答的准确性呢？**

因为 **AI 和我们人类是不一样的——你想让它思考，它就必须「说话」** 。我们可以这样理解：

- 大模型每输出一个字（ `Token` ），其实这个生成的过程就是在思考；
- 让它先吐出这些思考 Token，其实就是让它在那里自言自语——就像我们做数学题时写在草稿纸上一样，它一边写一边在草稿纸上不断验算，算出来发现错了就当场排除掉这个错误结果；等它最终把答案或工具调用给到你之前，其实已经在草稿纸上验算过很多遍了；
- 反过来，如果你不让它把这些思考过程先「说」出来，它是没有办法在脑子里凭空思考的。

看懂了这个底层原理，你平时在 AI Agent 界面上每天看到的两个功能就彻底明白了：

- **思考档位（ `Reasoning Effort` ：从低到高 `Low / Medium / High / Max` ）** ： 它本质上影响的就是 **模型在思考过程中输出 Token 的长度** 。你可以理解为：模型每多输出一个思考 Token，就多思考了一下；脑子转得越久，最终给出的结论自然就越准确（从原理上讲，思考程度越高给出的答案肯定越准确，不用轻信网上所谓“高档位比 Max 档位更准”的说法）。
- **`Plan` 模式（规划模式）** ： 规划模式和思考有点类似，但它会把思考后接下来要做的事情 **写到一个计划文档里面去** 。这个文档很多时候其实主要是 **给人看的** （让你在它动手前大概知道它接下来要做哪些事情，方便确认方向），或者是 **把计划内容沉淀下来给不同的 AI Agent 看** （比如压缩了上下文或者换了新对话窗口之后，后续的 Agent 还能看到之前的完整计划），并不是说单靠把思考结果写进文档里，它后续执行就一定更准确。

## 三、从 Function Calling 到 MCP：它为了解决什么问题？

到了 **2024 年** ，市面上涌现出了越来越多的 AI 客户端软件（比如 Cursor、Windsurf 等）。大家不再满足于只让 AI 在本地读写文件了，而是希望它能够去连接外部的各种软件和数据源——比如读 GitHub 仓库、读写 Notion 笔记、查云端数据库、或者读取 Figma 的设计稿。

但这时候，大家在工程上遇到了一个难题： **各家软件的工具接口格式是互不相通的，每个人都在重复造轮子。**

![MCP 统一连接外部服务的初衷与开启后全量工具说明常驻挤占初始上下文的对比](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/04-mcp-protocol-and-cost-v1.svg)

MCP 统一连接外部服务的初衷与开启后全量工具说明常驻挤占初始上下文的对比

当时不同 AI 接口定义 `Tool` 的写法都不一样：如果某个办公软件想让 10 家不同的 AI 客户端都能连上自己，它就得写 10 套对接代码；反过来，每当有一个新的 AI 客户端出来，如果不跟其他人对齐，又得让所有外部软件去写一套新的接口。

为了解决这种接口碎片化的问题， **Anthropic 在 2024 年 11 月 25 日发布并开源了 `MCP` （Model Context Protocol，模型上下文协议）** 。

如上图左半边所示，MCP 的作用就是在 AI 软件和外部服务之间定了一个 **统一的转接标准** ：

- 假设我们想给各种 AI 客户端开放访问自家软件的权限，只需要按照 Anthropic 的规范写一个叫 **`MCP Server`** 的程序；
- 只要写好这一个 `MCP Server` ，所有支持 MCP 协议的 AI 客户端就全都能直接连上来读取我们软件的功能了。

当时 MCP 刚出来的时候，我在团队里正好就是负责写 `MCP Server` 的，所以对它的工作机制和里面的坑都很有体会。

**`MCP Server` 和 AI Agent 之间是怎么配合工作的呢？** 其实它的底层原理和前面讲的 `Function Calling` 是差不多的：

1. 假设我给 AI Agent 装了一个 GitHub 的 MCP，里面提供了两个工具（一个「读代码仓库」、一个「写代码仓库」）；
2. 当我跟 AI Agent 对话时，客户端就会把这两个工具的说明一起打包发送给云端大模型；
3. 大模型分析我发给它的这句话（比如「帮我读取一下我的仓库」），判断出需要调用「读代码仓库」的工具，于是以 **`JSON` 格式** 把调用指令发回给我们本地的 AI 客户端；
4. 本地 AI 客户端通过 **MCP 服务** 去调用对应的接口（比如 GitHub API），读取到仓库里的代码之后，再通过 MCP 响应给 AI 客户端，最后由客户端塞回给云端的大模型。

如果一个 MCP 服务里只写了两个工具，这套流程跑起来完全没问题。 **但为什么后来很多深度使用 AI Agent 的朋友，反而越来越少用 MCP 了呢？**

看一眼上图右半边就能明白，MCP 在实际使用中暴露出了两个很明显的痛点：

1. **工具多的时候，一句话还没说，上下文就已经非常长了** ： 假设我在一个 MCP 服务里写了二三十个工具（读代码的、写代码的、管分支的、查 Issue 的……），每一个工具发给大模型时，都必须包含三样东西： **工具的名称、工具的描述、以及工具的 `Schema` （也就是告诉模型调用这个工具时需要填哪些参数、每个参数是什么格式）** 。单是一个常见 MCP 服务的工具说明往往就要占掉 **`4,000 到 8,000 个 Token`** 。 只要你装了 GitHub、Figma 这些 MCP， **每一次新开一个对话话题，哪怕我们一句话都还没说，客户端就必须把这几十个工具的名字、用途和参数 `Schema` 全部塞进初始 `Context` （上下文）里面去** ，起步上下文就已经非常长了。
2. **本地后台运行与跨客户端配置的摩擦** ： MCP 本质上是一个服务进程。尤其是在 MCP 刚出现的时候，很多 MCP 都得在你自己电脑后台跑一个本地服务（现在虽然有不少改成了云端长连接的 MCP，不用本地起服务了）；而且早期接入不同 AI 客户端时坑也蛮多的——比如有的客户端最多只支持挂载 30～40 个工具，排错和鉴权机制也没那么完善，经常出现「你的 MCP 服务在这个 AI 客户端里能用，换到另一个客户端就得重新配一遍，甚至直接报错用不了」的情况。

## 四、终端与文件标配之后：按需搜文件与「看 Skill 调 CLI」

### 1\. 对内查资料：从早期 RAG 向量库到按需搜文件

到了 **2025 年之后** ，能力更强的新一代 AI Agent 出现了。这时候行业对 AI Agent 形成了一个共识： **大家都默认 AI Agent 里面一定要内置「文件读写」「搜索文件」以及「在终端执行命令」这几样基础工具** ；同时，大模型自己搜文件、写命令、自己规划任务的能力也突飞猛进。

这一变化，让 AI **「对内去项目里查资料」** 和 **「对外连接第三方工具」** 的方式双双迎来了轻量化改造。我们先看它怎么改变了 **去项目里面查资料的方式** 。

在早期，有一种让 AI 去项目或知识库里查资料的主流方式，叫做 **`RAG` （检索增强生成，也就是常说的向量知识库）** 。

**什么是 `RAG` 向量知识库呢？** 假设我们有一个很大的项目代码仓库，或者有很多份 Figma 官方文档，AI 本身训练时的知识不足以回答好具体问题，也没法把几百份文件一次性全塞进上下文里。早期 `RAG` 的做法是：

1. 先把所有文档或代码 **切成一个个小碎片** ；
2. 把这些文本字符串转换成数学上的 **「向量」** （即一串代表语义的数字坐标，意思越相近的句子算出来的数字越接近），存进专门的 **向量数据库** 里（或者在编辑器里提前建好向量索引）；
3. 当你每次提问（比如「Figma 里怎么修改图层」或问一个业务代码问题）时，程序就拿你问题里的关键词去和向量数据库做匹配（召回），找出 **意思最相近的那几段文本或代码碎片** ，一起丢给云端的大模型。

听起来很合理，但在实际写代码、做项目时， `RAG` 向量知识库有两个很大的硬伤：

- **第一，代码仓库变动非常频繁，转成向量是有计算开销的** ： 我们写代码时文件每分钟都在改动，而把代码文本转换成向量需要专门的运算开销；一旦刚改完代码还没来得及重新索引，搜出来的就是过期的旧代码；
- **第二，切碎文档会破坏原本的结构，按「意思相近」经常找不准具体报错位置** ： 一篇完整的文档或代码文件，如果你硬把它切成小碎片，它原本的上下文结构就被破坏掉了——你不知道该从哪一段开始切，切开后 AI 也不知道前后文能不能关联得上。所以在修代码报错时，只按模糊的「意思相近」去搜，经常找不准具体的报错位置。

**那现在的 AI Agent 是怎么做的呢？**

现在的 AI Agent 直接 **放弃了本地向量库机制，改成完全模仿「人类程序员」的工作方式去搜文件** ：

- 我们人类程序员写代码遇到某个地方报错时，是怎么找代码的？我们肯定是先找到一个能定位那段代码的关键词，先去 **全局搜索文件内容（比如用 `grep` 工具）** ；
- 搜出来几个文件之后，先看一眼这几个文件的名字（或者直接 **按文件名规律用 `glob` 工具筛选** ）大概是干嘛的；
- 找到目标文件点进去之后，在文件内部再做一次局部搜索，精准定位到那几行代码，然后直接修改。

现在的 AI Agent 就是直接调用内置的搜索工具去搜本地文件。这样做一下子就解决了前面 `RAG` 的两个痛点： **一是代码写完之后不需要再做任何向量化处理，读到的永远是最新的代码文件；二是只要大模型能基于你的问题想好搜索关键词，按关键词精准搜索代码其实非常准确。**

Vercel 团队在 2025 年写过一篇非常经典的复盘 [《为什么我们删掉了 Agent 80% 的工具》](https://book.oiloil.org/articles/we-removed-80-percent-of-our-agents-tools) ：他们早期花了几个月时间搭建了 17 个专用的检索工具去查自家产品资料，结果系统又慢又容易出错；后来他们直接砍掉了 80% 的定制工具，只留给 AI **读写本地文件和跑终端命令** 的能力，结果查询速度快了 **3.5 倍** 、Token 开销少了 **37%** ，任务成功率反而从 **80% 升到了 100%** 。也就是说，现在让 AI Agent 自己用基础工具去搜索调研，它已经解决得非常好了。

### 2\. 对外连工具：为什么 CLI 比 MCP 更轻量？

对内查项目资料靠自己搜文件解决了，而自从「文件读写」和「跑终端命令」成为 AI Agent 的标配之后，大家也开始意识到： **连接外部工具（比如查 GitHub 有哪些仓库、操作飞书表格），除了让 AI 直接调平台的开放 API 之外，我们还有一种比 MCP 更加优雅的解决方式——直接配置一个 `CLI` 。**

![Agent 通过终端命令调用系统 CLI 实现平时零上下文占用与跨软件通用的三大优势](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/05-cli-zero-context-advantage-v1.svg)

Agent 通过终端命令调用系统 CLI 实现平时零上下文占用与跨软件通用的三大优势

先给刚入门的朋友讲讲什么是 **`CLI` （Command Line Interface，命令行工具）** ：

- 我们平时在电脑上用的带界面的软件（比如飞书桌面客户端），叫做 **`GUI` （图形用户界面）** ——它给你一个很丰富的可视化 UI 页面，让你用鼠标去点击各种按钮来操作；
- 而 **`CLI` （命令行工具）** ，就是在电脑终端命令行窗口里操作的工具（比如 GitHub 官方有 `gh` 命令行工具，飞书也有官方命令行工具）——我们跟它交互的方式不是用鼠标去点页面，而是直接输入一行文本命令。

以前之所以会有 CLI，是因为程序员有很多自动化任务需要通过程序去运行，程序没办法自己去点图形界面； **而到了 AI 时代，这个早已有之的 `CLI` ，天然就成了外部程序和 AI Agent 之间最好的交互方式！**

为什么呢？因为如果你让 AI Agent 去操作带画面的 `GUI` 界面，它得动用多模态能力先去「看」你的 UI 截图、识别按钮位置再去点击，交互链路又长又慢； **而 `CLI` 对大模型来说太简单了——纯文本输入、纯文本输出，这恰恰是大语言模型最擅长的事情。**

相比前面提到的 MCP，直接用 **`CLI`** 来连接外部工具，有三个非常明显的优势：

1. **平时 0 上下文占用，需要时再用 `--help` 即查即用** ： 前面提到，MCP 里提供的工具一多，每次对话哪怕一句话不说，都会把几十个工具的描述塞进上下文；而 **CLI 只是装在你本地电脑里的一个普通程序，默认完全不会往 AI 大模型的上下文里输入任何额外信息** 。 而且很多大型 SaaS 产品的官方 CLI（比如 `git` 、 `gh` 等），大模型在训练的时候就已经知道它的命令怎么写了，调用时根本不需要占用上下文；就算遇到一些比较复杂的子命令参数，AI 在需要用的时候自己运行一句 `--help` （命令行自带的查看帮助指令）查一下有哪些命令就行了，用完即走。
2. **通用性极强，装一次所有 AI Agent 都能直接用** ： 因为 CLI 这种形式早就存在了，任何 AI Agent 只要具备调用终端命令的能力，就肯定能直接使用电脑里的 CLI；而且 CLI 的登录鉴权机制非常成熟，不需要像 MCP 那样换一个客户端又得重新配置一遍。
3. **复杂操作可以让 AI 写进脚本里一次性跑完** ： 如果你用 MCP 去执行一个包含几十步的复杂操作，AI 就得在循环里一次接一次地反复调用工具；而用 CLI 的话，你可以直接让 AI Agent 写一个脚本（在脚本里组合调用 CLI 的命令），然后直接运行这整个脚本，一个复杂的批量任务就一次性执行完成了。

### 3\. 为什么 CLI 还要搭配 Skill 一起用？

那为什么我们说 **`CLI` 还要搭配 `Skill`** 一起用呢？

大家现在对 `Skill` 应该听得比较多了（还不了解的朋友可以先看 [《从 0 到 1 了解什么是 Skill》](https://book.oiloil.org/articles/skill-guide) ）。简单来说， **`Skill` 其实就是电脑里的一个文件夹** ，里面放着说明文档（ `SKILL.md` ）或辅助脚本，用来告诉 AI Agent「遇到某类任务时有哪些工作流程、或者给你补充哪些新的业务知识」。

在连接外部工具时， **`Skill` 的作用就是告诉 AI Agent：你怎么样去调用这个 `CLI` ，才能符合我手头的具体业务流程。**

为什么光有 CLI 还不够？因为 **光有 CLI 工具，AI 只是知道「怎么敲命令」，但它并不知道你具体的业务应该按什么流程去做** 。

举个最直观的例子：

- 假设你电脑上已经装好了 **飞书 CLI** ，但是你的飞书账号里面有几十张不同的表格；
- 当你直接对 AI 说一句「帮我记一个新选题」的时候，AI 根本不知道应该往哪一张表格里面去写；
- 而如果你写了一个 **`Skill`** ，在里面告诉它：「我的自媒体选题是写到哪张飞书表格里的（附上表格标识与字段要求）、应该按什么步骤调用飞书 CLI」——那么平时这个 Skill 只在上下文里占一句话的目录简介；等你提到「记新选题」时，AI 一读这个 Skill 文件夹，就能立刻把 **你的业务规则（ `Skill` ）** 和 **底层的命令行工具（ `CLI` ）** 搭配起来，准确无误地把选题写到对应的飞书表格里去。

## 五、从提示词工程、上下文工程到 Harness 工程

在 **2023 年到 2026 年** 这几年时间里，有三种「工程方式」是我们平时听到最多的： **提示词工程（Prompt Engineering）** 、 **上下文工程（Context Engineering）** 和 **Harness 工程（Harness Engineering）** 。

其中最早出现的 **「提示词工程」** 前面我们已经聊过了，它其实就是教你怎么样按固定的结构去把单次提问的提示词写好。那后面出现的「上下文工程」和「Harness 工程」又分别是在解决什么问题？它们两个之间到底有什么区别？

### 1\. 上下文工程（Context Engineering）：管理急剧膨胀的模型记忆窗口

为什么在 AI Agent 出现之后，大家突然开始高频讨论 **「上下文工程」** 了呢？

因为 **在 AI Agent 里，上下文（ `Context` ）膨胀得太快了** 。以前我们手动跟聊天 AI 对话，一次输入的提示词顶多也就几千个字；但是当 AI Agent 开始自己在循环里跑任务、自己去读代码文件时，动不动一下子就是几十万字的上下文。

![上下文工程的三大核心机制：前缀缓存复用、满载自动压缩与本地文件持久记忆](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/13-context-engineering-three-pillars-v1.svg)

上下文工程的三大核心机制：前缀缓存复用、满载自动压缩与本地文件持久记忆

这时候， **每一轮对话该往大模型的上下文窗口里塞什么东西、要删掉什么东西、怎么排列它们的先后顺序才能既省钱又能命中缓存、以及当这个窗口快满的时候怎么去压缩** ，就成了一个比单纯写提示词复杂得多的工程问题：

- **可介入的环节变多了** ：以前我们只能改对话的提示词；现在在 AI Agent 里，我们可以去改工具的描述、可以去改自己工具返回的响应格式（让工具别返回一长串没用的废话）、还可以去控制压缩上下文的策略；
- **排列顺序以命中前缀缓存（ `Prompt Caching / KV Cache` ）** ：大模型是从第一个字往后按顺序计算的，只要把固定不变的系统提示词和规则放在最开头，把每一轮新增的对话、工具结果或按需读入的 `Skill` 正文严格追加在最末尾，云端就能直接复用前面算好的缓存，省下高达 90% 的重复计算费用（详见 [《大模型的注意力机制与 KV Cache》](https://book.oiloil.org/articles/llm-attention-and-kv-cache) ）；
- **窗口快满时砍掉无用信息（自动压缩 `Compaction` 与文件记忆）** ：当长任务快把上下文窗口塞满时，软件会自动触发上下文压缩，砍掉前面对于后续任务已经没用的冗长过程日志，或者把关键任务进度写进本地 Markdown 文件（如 `todo.md` ）里跨窗口接力（详见 [《了解 AI Agent 的常用操作》](https://book.oiloil.org/articles/ai-agent-common-operations) ）。

一句话总结， **上下文工程的核心目标，就是通过程序手段保护大模型有限的注意力——防止它跟我们聊久了、读的文件多了之后，因为信息过载而出现「降智」。**

### 2\. Harness 工程（Harness Engineering）：为什么比上下文工程更进一步？

到了 2025 年底至 2026 年，大家又听到了一个比上下文工程更进一步的新词： **`Harness` 工程（Harness Engineering）** 。

`Harness` 这个英文词原本的意思是 **给马匹穿戴的缰绳、马鞍和马车套具** ；放到 AI 领域里，我们可以把 `Harness` 工程理解为 **「驾驭大模型的整套外层软件工程」** 。

![Harness 工程的三大核心职责：安全沙盒护栏、客观自检闭环与外部操作三级阶梯](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/14-harness-engineering-closed-loop-v1.svg)

Harness 工程的三大核心职责：安全沙盒护栏、客观自检闭环与外部操作三级阶梯

很多朋友刚听到这个词时都会疑惑： **我其实没太懂「上下文工程」和「Harness 工程」的本质差别是什么？为什么有了上下文工程之后，还要再提出一个 Harness 工程？**

其实， **上下文工程和 Harness 工程有一部分是交叉的** 。比如我们设计一个 AI Agent 时，它的工具怎么设计、工具描述怎么写、以及工具调用报错之后怎么处理能让 AI Agent 更好地理解——这部分工作既是在做上下文工程，也是在做 Harness 工程。

**但是，Harness 工程包含的范围比上下文工程更大。** 因为上下文工程最主要关心的只是「模型上下文窗口内部的信息管理」；而在真实的 AI Agent 开发里，还有很多 **偏向软件程序与外部环境设计的工作，它们跟「上下文」的关联其实没有那么大** ：

1. **在程序里拦截高危操作与安全沙箱（ `Sandbox` ）** ： 比如当 AI 调用工具要去删代码的时候，如果只靠在提示词里叮嘱它「千万别删本地代码仓库」，聊久了模型还是可能会犯错。所以在做 AI Agent 软件时，我们会在本地程序里去判断：一旦识别到 AI 要执行高危删除命令，程序就直接阻止它删除；或者给云端/本地的 AI Agent 套上一层操作系统级的 **安全沙箱（Sandbox）** ，从软件权限上防止 AI 删库闯祸。 像这种「在程序里判断并阻止高危命令」的行为，显然就不属于管理模型记忆的「上下文工程」了，它属于 **Harness 工程** 的一部分。
2. **开发驱动循环的外部工具与客观验收闭环** ： 除了包含上下文管理模块，Harness 还要负责大模型外部的一整套软件系统——包括提供文件读写工具、提供浏览器操作工具（比如遇到没有 CLI 的网站时，通过浏览器自动化工具去操作网页，详见 [《AI Agent 浏览器自动化与电脑自动化指南》](https://book.oiloil.org/articles/agent-browser-automation) ），以及在模型改完代码后自动运行测试与浏览器检查、发现报错自动打回重修的验收闭环。 试想一下，当你给 AI Agent 开发一个浏览器自动化工具时，虽然它最终也是为了给大模型返回上下文信息，但你在开发这个工具的过程中涉及大量的软件程序设计——如果把写浏览器工具、做安全沙箱、做权限鉴权全都叫做「上下文工程」，听起来就会非常奇怪。

**所以说，行业并不是为了硬造一个新名词才提出 `Harness` 工程；正是因为之前「上下文工程」这个名字表达得不够完整、不够准确，后面才提出了范围更大的 `Harness` 工程。** 现在我们做 AI Agent 开发里面的所有外层软件流程，都可以统称为 Harness 工程。

## 六、把历史串成全景：核心概念配合与周边名词

### 1\. 一段话 + 一次真实任务，看懂所有概念是怎么配合的

顺着从 2022 年底到 2026 年的时间线一路看下来，你会发现前面提到的这些概念现在在所有 AI Agent 里都是普遍通用的（在 **2025 年 12 月** ，OpenAI 与 Anthropic 等厂商还联合在 Linux 基金会下成立了 **Agentic AI Foundation** ，正式把 **`AGENTS.md`** 、 **`MCP`** 与 **`Agent Skills`** 确立为跨厂商通用的开放标准）。

理解了它们各自的意思之后，我们可以用下面这段话，把今天聊的所有核心概念一口气串起来：

- **我们现在给 AI Agent 提的这些问题** ，就是 **`Prompt` （提示词）** ；
- **提示词加上我们过往调用工具的历史信息、以及 AI 给我们的回复** ，再一起丢给大模型，这所有的信息合在一起就叫做 **`Context` （上下文）** ；
- **我们的 `Skill`** ，本质上是一种 **按需给 AI Agent 提供提示词与业务流程** 的方式；
- **想让 AI Agent 去连接外部的工具** ，你既可以通过 **`CLI` （命令行）** 的方式，也可以通过 **`MCP`** 的方式——其实它们两个之间没有很大的本质差别，都是在本地去调用程序、然后再去获取外部的数据，只是 CLI 平时不占上下文、用起来更轻量通用；
- **而关于提示词工程、上下文工程和 `Harness` 工程** ，现在的 **`Harness`** 就包含了前面的两个工程——整个围绕 AI 大模型的本地外层软件开发（不论是上下文管理、工具设计、沙箱设计，还是一些安全措施与鉴权机制），我们都可以把它称为 **Harness** 的一部分。

### 2\. 顺手理清四个周边概念：App、Plugin、Subagent 与 Hook

除了上面这条主线，大家平时在 AI Agent 软件界面上还会看到另外四个技术名词： **`App` 、 `Plugin` （插件）、 `Subagent` （子 Agent）和 `Hook` （钩子）** ，最后我们也顺手把它们讲清楚：

![App 网页授权、Plugin 扩展包、Subagent 独立上下文与 Hook 自动检查的定位分工](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/08-surrounding-concepts-map-v1.svg)

App 网页授权、Plugin 扩展包、Subagent 独立上下文与 Hook 自动检查的定位分工

- **`App` （应用连接器）——产品化的 MCP** ： 我们在 Codex 等软件界面里看到的 `App` ， **本质上可以理解为一个「产品化的 MCP」** 。 以前我们自己去配置一个 MCP 的时候，往往要手动去填一个服务地址或者填一串 `API Key` ；而 `App` 就相当于软件已经帮你把 MCP 的配置预制好了，还给你做成了一个带产品图标的按钮——你点一下「连接」，本质上就是帮你把 MCP 配置填了上去，然后跳到对应网站里点一下「同意授权」拿到鉴权信息，就直接连接成功了。
- **`Plugin` （插件）——比 Skill 更上一层的能力打包** ： `Plugin` 就是把不同的能力组合打包在一起。比如我可以把 `Skill` 加上 `CLI` 打包成一个 Plugin，或者把服务于同一个功能的几个 `Skill` 和 `MCP` 服务搭配在一起。 举个例子，如果我做一个「自媒体插件」，里面可以把做封面的 Skill、生成字幕的 Skill 以及配套工具全部装在一起，大家装这一个插件就能用整套功能，不用再去挨个安装很多个独立的 Skill 了。
- **`Subagent` （子 Agent）——主 Agent 派发出去的独立助手** ： `Subagent` 就是我们当前对话的「主 Agent」底下派发出去的一个子 Agent。你可以把它理解为一个同样能独立执行任务的 Agent，只不过 **我们不直接和子 Agent 去对话** ——当遇到需要翻找大量资料的支线任务时，主 Agent 派子 Agent 在它自己独立的上下文里把任务执行完，最后子 Agent 只把精简的任务总结丢回给主 Agent，从而保护主对话的上下文不被塞满（详见原创 [《怎样用好子 Agent》](https://book.oiloil.org/articles/subagent-workflow) 与精选收录 Cognition 团队的 [《不要构建多 Agent 系统》](https://book.oiloil.org/articles/dont-build-multi-agents) ）。
- **`Hook` （自动触发钩子）——特定时机自动执行的本地程序行为** ： `Hook` 就是一种自动触发的钩子。我们在跟 AI Agent 对话和执行任务的过程中会有很多时机——比如 AI 刚刚调用了修改代码的工具，或者 AI 已经把所有任务都执行完成、给出了最终响应。我们可以在任意一个时机去自动触发一些本地程序操作（比如写完代码后自动触发一次代码检查）， **这个过程完全是由我们预设的程序触发的，不需要大语言模型自己去关心** 。 当初设计 `Hook` 这个机制，主要是为了让人有更多的时机去介入和规范 AI Agent；现在随着模型能力越来越强，很多时候不需要配 `Hook` ，AI Agent 自己改完代码也会主动去检查了。因此现在 `Hook` 更多用于我们自己去开发一些定制化的 AI Agent（比如做 Personal Agent 时，规定在什么时机固定触发什么样的程序行为）。

### 3\. 日常使用 AI Agent 的四条实用原则

最后，落到我们平时自己使用 AI Agent 的日常习惯上，可以把前面的原理浓缩成四条最实用的原则：

![日常使用 AI Agent 时在全局规则、Skill、CLI 与 MCP 之间的选型判断指南](https://book.oiloil.org/assets/articles/ai-agent-principles-and-ecosystem/09-four-selection-principles-v1.svg)

日常使用 AI Agent 时在全局规则、Skill、CLI 与 MCP 之间的选型判断指南

1. **连接外部平台时，优先用「 `CLI` + `Skill` 」代替繁重的本地 `MCP`** 凡是有官方命令行工具的平台（如 GitHub、飞书、Vercel 等），优先让 AI 帮你在电脑上装好 `CLI` 并配合 `Skill` 使用，平时 0 上下文占用且跨软件通用；没有 CLI 但有网页后台的可以用浏览器自动化；只有特殊场景才按需保留少量 `MCP` 或一键授权的 `App` 。
2. **开头的全局规则（ `AGENTS.md` ）保持精简，具体业务流程放进 `Skill`** 项目根目录的 `AGENTS.md` （或 `CLAUDE.md` ）每次都会常驻在 `Context` 最开头，只写百行以内的项目结构与常用命令即可；像写文章、做封面、管表格这类具体业务流程，一律放进独立的 `Skill` 文件夹里让 AI 按需读取。
3. **遇到复杂重复的批量操作，让 AI 写成脚本去调用 `CLI`** 不管是处理数据还是批量调外部接口，不要让大模型在循环里一次次手动调工具；直接让它写一个脚本去执行 `CLI` 命令并放到 `Skill` 的 `scripts/` 目录里，既省 Token 又快又稳。
4. **保护上下文窗口的干净度，一个话题只干一件事** 记住「上下文越精简干净，模型注意力越集中、执行效果越好」。不要在同一个对话窗口里把毫不相干的任务混在一起聊，做完一个独立任务就随手新开一个干净窗口。

## 总结

回顾从 2022 年底 ChatGPT 诞生到今天现代 AI Agent 的整条时间线，你会发现所有技术名词的演进其实都顺着一条非常清晰的逻辑：

1. **从「纯文字聊天」到「动手干活并自主循环」** ：早期 `Prompt` 只能让模型回复文字；为了能操作电脑，出现了用固定格式 JSON 字符串让本地软件代为执行的 `Function Calling（Tool）` ；为了在遇到报错时不直接停工，出现了根据反馈继续下一步的 `ReAct` 循环；而随着 o1、DeepSeek-R1 等原生推理模型（ `Thinking` ）取代死板的固定工作流（ `Workflow` ），AI Agent 终于能自己在长循环里稳稳跑完复杂任务。
2. **从「全量硬塞上下文」到「按需轻量化加载」** ：因为模型本身是无状态的，每次对话都要重发整份 `Context` ，且上下文越杂乱模型越容易分心降智——所以对内查资料从早期切碎文档的 `RAG` 向量库，演进成了像人类程序员一样直接按关键词搜文件；对外连工具也从一开启就塞满几十个工具描述的 `MCP` ，演进成了平时 0 占用的 `CLI` 加上按需翻开的 `Skill` 文件夹。
3. **从「写好单句提示词」到「构建外层 Harness 系统」** ：工程的重心从早期的「提示词工程」，走到管理几十万字窗口与缓存压缩的「上下文工程」，最终升级为涵盖上下文管理、工具设计、安全沙箱与自动验收闭环的「 `Harness` 工程」。看懂了这条演进线，以后无论再遇到什么新概念，你都能一眼看清它在整套系统里的位置。
