哈喽大家好，我是欧呦，这篇文章将为大家分享《从 0 到 1 学 Vibe Coding》的第二课：Vibe Coding 必备的研发与 AI 基础概念。

很多刚接触 AI 编程的朋友都会有一个疑问：现在 AI 写代码的能力已经这么强了，我们平时开发产品只需要在对话框里用自然语言提需求，一行代码都不用自己手敲，那为什么还要花时间去了解这些研发和 AI 的基础概念？

下面我们就先聊聊为什么懂一点基础概念能让你在 Vibe Coding 时少走很多弯路，再把做一个 AI 时代的个人开发者必须掌握的 **前端工程概念、前后端与网络存储概念，以及大模型 API 接入概念** 梳理清楚。

## 为什么要懂研发与 AI 概念

### 1\. 获得对产品的掌握度

在实际使用 AI 写代码时，不同模型的能力是有明显差距的。如果我们使用的是最顶尖的模型，做一个简单的展示页面，确实哪怕很多概念都不了解也能做出来；但如果我们平时想要节省开销，或者受限于条件没有办法随时用上最强的模型，情况就会完全不同。

当面对稍微复杂的任务、AI 没法写出符合预期的代码或者做出来的效果不好时，如果你懂基础的研发与 AI 概念，你就能作为主导者主动介入，直接给 AI 提出方向性的见解（比如提醒它「这里把组件拆出来」「这里接口返回改成 JSON 格式」）。更重要的是，我们要对自己做出来的东西有 **掌握度** ——如果你完全不知道它底下是怎么跑起来的，这个产品真要上线给别人用时，你心里会非常没有信心。

### 2\. 长期产品需要懂概念的人把关

我认为， **任何一个已经上线的产品，如果想要长期稳定地运营下去，就一定要至少有一个懂研发概念的人在盯着** ——即便现在 AI 写代码已经很强了也是如此。

如果有人说自己真的是纯零代码基础、连基本的工程概念都不了解，却同时维护着好几个线上项目，那他的项目大概率是很不靠谱的。因为当你完全没有工程架构意识、也没有建立认真的代码检查（Review）流程，只是单纯让 AI 闷头堆代码时，前面一两个功能可能看起来很快，但等到你后续不断往上堆新功能的时候，就会发现 **每加一个功能都异常艰难** ：历史代码和上下文已经杂乱不堪，AI 自己读着都犯迷糊，而你自己又看不出结构问题在哪、给不出有效的修改洞察，整个开发过程就会变得非常煎熬。

### 3\. 为什么做产品首选 Next.js

在 [《了解 AI Agent 的常用操作》](https://book.oiloil.org/articles/ai-agent-common-operations) 里，我们介绍过可以让 AI 生成一个单文件 `.html` 来快速查看排版效果。但在实际做产品时，很少有一个单文件 HTML 就够用的情况——因为一个正常的产品起码要有完整的交互、多页面切换或者数据读写；如果从头到尾只有一个静态 HTML 文件，严格来说甚至算不上是一个真正的产品。

在绝大多数真实项目里，我们都会使用 **[Next.js](https://nextjs.org/)** 这类现代前端框架（所谓「框架」，就是一套已经帮你提前搭好标准文件夹结构和基础功能的工程骨架，不用从零砌砖；像大家熟悉的 [Notion](https://www.notion.so/) 、 [Stripe](https://stripe.com/) 、 [OpenAI](https://openai.com/) 等知名产品的网页端，底层广泛使用的都是 `React` / `Next.js` 这套技术体系）。为什么在 Vibe Coding 时代我最推荐大家用 `Next.js` ？核心有三个原因：

1. **它是目前全球最主流、AI 最熟悉的框架** ：因为全球有海量的优秀开源项目是用 `Next.js` 写的，大模型在训练时见过最多的就是它的代码，所以你让 AI 用 `Next.js` 写功能时，它最熟练、最不容易出错；
2. **天然对 SEO（搜索引擎收录）友好** ：做出来的网站更容易被 Google、Bing 等搜索引擎抓取到，为你带来免费的自然流量（具体原理我们在下一节马上拆解）；
3. **支持「前后端一体」开发** ：在同一个 `Next.js` 项目文件夹里，既可以写用户看到的网页界面，又可以直接写处理数据与调用大模型的后端接口，对于 AI Agent 在一个项目里统筹修改代码来说非常方便。

## 前端与工程结构核心概念

当我们让 AI 使用 `Next.js` 创建一个正式项目后，平时跟 AI 沟通需求或看它改代码时，最常遇到下面这四个核心工程概念：

### 1\. 组件化与函数化

如果不加约束地让 AI 在一个文件里不停加代码，很快这个文件就会膨胀到几千行，AI 每次修改都要把几千行代码重新读一遍，既浪费 Token（大模型处理和计费文字的最小单位，可以简单理解成字或词块）又极易改坏其他地方。解决这个问题靠的就是 **组件化** 和 **函数化** ：

- **组件化（Component）** ：就是把前端页面上的各个模块（比如顶部导航栏、按钮、价格卡片、弹窗）单独抽出来，写成独立的小文件进行复用。这样做有两个直接好处： **第一是可以大幅节省 Token** （修改导航栏时 AI 只需要读导航栏这一个几十行的小文件）； **第二是能够规范整个系统的设计** ，改一处按钮组件的样式，全站所有用到这个按钮的地方都会自动同步更新。
- **函数化（Function）** ：就是把项目里一些重复用到的代码逻辑封装在一起，起一个名字。比如网站里好几个地方都需要「把电脑底层的原始时间数字转换成『2026年10月30日』的显示格式」，或者「根据用户等级计算折扣后的价格」，让 AI 把这段逻辑封装成一个独立的函数，以后哪个页面需要算价格，直接调用这个函数名就行，不用把同样的计算代码到处复制粘贴。
![组件化拆分 UI 模块与函数化封装复用逻辑](https://book.oiloil.org/assets/articles/ai-and-dev-core-concepts/02a-component-and-function-reuse-v1.svg)

### 2\. JS 与 TS 的区别

要理解这两个词，我们先用一句话分清网页开发最基础的三剑客：

- **`HTML`** ：负责网页的骨架和文字内容（比如放一个标题、一个输入框、一个按钮）；
- **`CSS`** ：负责网页长什么样（比如字号多大、什么颜色、间距多少）；
- **`JavaScript` （简称 `JS` ）** ：是一门真正负责让网页「有交互逻辑」的编程语言——比如点击按钮后弹出提示框、切换深色模式、或者把用户输入的内容发给服务器，全都是靠 `JS` 实现的。

那什么是 **`TypeScript` （简称 `TS` ）** ？

简单来说， **`TS` 就是在 `JS` 的基础上多加了一层「类型检查」的更严格的语法。** 怎么理解「类型检查」有什么用？举个例子：假设我们在代码里写了一个计算订单总价的功能，规定传进来的「商品单价」必须是数字（ `number` ）。如果用普通的 `JS` ，万一 AI 在另一个地方写代码时粗心传了一段文字（比如 `"免费"` ）进来，写代码的时候根本不会报警，非要等用户真正在网页上点击结算、页面直接崩溃报错了才能发现；而如果用 `TS` ，因为语法严格规定了这里只能传数字，AI 刚把代码写完的那一秒，代码检查工具就会立刻标红提醒它：「这里类型不对，不能把文字传给只接收数字的位置」。

![JavaScript 与 TypeScript 类型检查对比](https://book.oiloil.org/assets/articles/ai-and-dev-core-concepts/02b-js-vs-ts-type-check-v1.svg)

JavaScript 与 TypeScript 类型检查对比

这一点在今天尤其重要： **在以前人类手写代码的时期，使用 `TS` 往往会增加写代码的复杂度和繁琐度；但在 AI 编程时期，我们根本不用关心这门语言写起来复不复杂（反正都是 AI 写），让 AI 统一使用更严格的 `TS` ，反而能从代码层面大幅减少 AI 犯错的可能性，让它自己更好检查、在运行前就自动把低级错误修掉。**

### 3\. SSR、CSR 与 SEO

很多朋友做出网站上线之后，当然希望别人在 Google 或百度搜索相关关键词时，能直接搜到自己的网站，从而源源不断地带来免费的 **自然流量** 。把网站做得更容易被搜索引擎搜到、排在更靠前的位置，就叫做 **`SEO` （Search Engine Optimization，搜索引擎优化）** 。

那网站要怎么样才能被搜索引擎搜到呢？这就涉及到搜索引擎的 **「爬虫（Crawler）」** 是怎么工作的，以及 `CSR` 和 `SSR` 的区别：

- **搜索引擎爬虫的工作方式** ：Google、Bing 等搜索引擎每天都会派出成千上万个自动程序（也就是「爬虫」），顺着网址去访问你的网页源码，把页面里的标题、段落文字和链接读取下来，收录进搜索数据库里。
- **`CSR` （Client-Side Rendering，客户端渲染）的问题** ：早期的很多纯前端单页应用采用的是客户端渲染。当用户或爬虫访问网址时，服务器发过来的其实只有一个几乎空白的 HTML 空壳和一堆 `JS` 代码，要等用户的浏览器把 `JS` 下载并运行完之后，文字内容才会显示出来。这会导致两个问题：一是用户刚点开网页时会看到短暂的白屏加载；二是很多搜索引擎爬虫扫一眼发现 HTML 源码是个空壳，直接就离开了，根本抓不到你网页里的内容。
- **`SSR` （Server-Side Rendering，服务端渲染）的优势** ：像 `Next.js` 默认支持的服务端渲染，是在用户或爬虫访问网址的那一刻， **先在云端服务器上把标题、正文和数据全部拼成一份完整的 HTML 网页** ，再直接发送给浏览器。这样不仅用户点开链接瞬间就能看到排好版的文字，搜索引擎的爬虫一来也能一字不落地把页面上的所有文字抓走收录，对 `SEO` 获取自然流量非常友好。
![SSR 服务端渲染与 CSR 客户端渲染对 SEO 爬虫收录的影响](https://book.oiloil.org/assets/articles/ai-and-dev-core-concepts/02c-ssr-csr-and-seo-crawler-v1.svg)

SSR 服务端渲染与 CSR 客户端渲染对 SEO 爬虫收录的影响

### 4\. npm 与 package.json

我们在做项目时，不可能连日历选择器、图标、动画效果都让 AI 从零一行行写起，而是会直接使用社区里已经非常成熟的开源代码包（Package）。

- **`npm` （Node Package Manager）** ：就是帮我们把这些外部开源代码包下载、安装到当前项目文件夹里的命令行工具（比如你在终端里常看到 AI 自动运行 `npm install lucide-react` ，就是在用 `npm` 安装 `Lucide` 图标库）；
- **`package.json`** ：固定放在项目根目录下的一个清单文件。打开它你会看到两部分核心信息：一是记录了「当前这个项目一共安装了哪些外部代码包、各自的版本号是多少」；二是定义了这个项目的常用快捷命令（比如运行 `npm run dev` 启动本地预览、运行 `npm run build` 打包上线）。只要有这个 `package.json` 文件在，哪怕换了一台新电脑，运行一行 `npm install` 就能把项目所需的所有外部代码包完整恢复出来。

## 前后端分工、数据库与网络请求

搞懂了前端工程怎么组织代码之后，如果我们要做一个真正能保存数据、能登录账号的完整产品，前端和后端到底是怎么配合的？下面我们用一个最直观的例子——假设我们要开发一个 **「写日记的小程序 / 网页应用」** ——把前后端分工、数据存储与网络请求串起来讲清楚：

### 1\. 前端、后端与数据库各管什么

在这个「写日记应用」里，整个系统其实分成了三个角色在配合工作：

1. **前端（Frontend）——用户在屏幕上看得到、摸得着的一切** ： 比如写日记的标题输入框、正文编辑区、选择今天心情的小图标、「保存日记」按钮，以及历史日记列表的排版样式。用户在手机或电脑浏览器里直接点击和操作的界面，全都是前端负责的。
2. **后端（Backend）——在云端服务器上运行、负责处理核心逻辑与安全把关的程序** ： 用户看不见后端的界面。当你在前端写完一篇日记、点击「保存」按钮时，前端会把这篇日记的内容打包发送给后端。后端收到后，要先负责检查：「当前发请求的这个人有没有登录？他是不是这个日记本的主人？字数有没有超标？」确认没问题后，再由后端去把数据存起来。但凡涉及 **权限校验、扣费结算、核心业务规则和藏密钥** 的事情，都必须放在后端完成。
3. **数据库（Database）——专门用来长期、安全存放数据的云端仓库** ： 后端程序本身只负责处理逻辑，不负责长期存文件。当后端检查完你的日记没问题后，就会把「用户 ID、日记标题、正文内容、创建时间」写成一条规整的记录，存进云端的数据库（比如常见的 `PostgreSQL` 、 `Supabase` 或 `Neon` ）里。
![以写日记应用为例拆解前端界面、后端接口与云端数据库的三方分工](https://book.oiloil.org/assets/articles/ai-and-dev-core-concepts/03-diary-app-frontend-backend-db-v1.svg)

以写日记应用为例拆解前端界面、后端接口与云端数据库的三方分工

### 2\. 本地存储与云端数据库

很多新手在做第一个小工具时，经常分不清数据到底是存在浏览器里还是存在数据库里：

- **浏览器本地存储（ `localStorage` ）** ： 每个人的浏览器里都自带了一小块本地存储空间。如果你的「写日记工具」只是想做一个极简的纯前端小工具，不打算做账号注册登录，你可以让 AI 直接把日记保存在用户自己浏览器的 `localStorage` 里。这样做的好处是 **开发极其简单、完全不需要后端和数据库成本** ；但缺点也很明显——数据只存在当前这台电脑的这一个浏览器里，一旦用户换了手机打开网址、或者清理了浏览器缓存，之前写的日记就找不回来了。
- **云端数据库（Database）** ： 如果你希望用户在电脑上写完日记，拿起手机登录同一个账号也能立刻看到，或者你的产品涉及用户账号、会员订阅和多人协作，那就必须让 AI 接入真正的云端数据库。

### 3\. HTTP 状态码与环境变量

当用户在前端点击「保存日记」或「加载历史日记」，前端跟后端通信的过程就叫做 **发送网络请求** 。在这个过程中，有三个概念你在看 AI 调试报错时一定会遇到：

1. **`HTTP` 与 `HTTPS`** ： 它们是浏览器（前端）和服务器（后端）之间传输数据的通信协议。区别在于 **`HTTPS` 比 `HTTP` 多了一个代表安全的 `S` （Secure，加密传输）** 。比如你写的私密日记或者输入的登录密码，如果用不加密的 `HTTP` 发送，在网络传输途中很容易被别人截获偷看；而正式上线的网站都会使用 `HTTPS` ，把传输内容全程加密锁起来。
2. **看懂 4 个最常见的 HTTP 状态码（Status Code）** ： 每次前端给后端发请求，后端都会返回一个三位数的状态码告诉前端结果怎么样。你只需要记住最常见的 4 个：
	- **`200` （成功）** ：一切正常，日记已经成功保存或读取回来了；
		- **`401` / `403` （未登录 / 没权限）** ：比如你的登录过期了，或者想访问别人的私密日记被后端拦住了；
		- **`404` （找不到地址）** ：前端请求了一个根本不存在的网址或后端接口地址（比如把收发数据用的地址 `/api/diary` 拼错了）；
		- **`500` （服务器内部错误）** ：前端发请求的方式没问题，但是 **后端程序自己写出了 Bug 或者连不上数据库崩掉了** 。平时你在浏览器控制台看到 `500` 报错，直接把后端的报错日志复制给 AI 让它修后端代码即可。
3. **环境变量（`.env` 文件）——绝不能写死在前端代码里的秘密** ： 后端要想连接云端数据库，或者调用后面要讲的大模型接口，都需要用到密码和密钥。新手最容易犯的一个致命错误，就是让 AI 把密码直接写死在前端代码里——任何懂一点技术的人只要在你的网页上按下 `F12` 打开浏览器开发者工具，就能把你的密码直接看光盗走。正确的做法是： **把所有数据库密码、API 密钥全部写进项目根目录下名叫 `.env` （或 `.env.local` ）的「专属密码本文件」里（专业上叫环境变量文件），代码里只写「去读取 `.env` 里的某某钥匙」，只允许后端程序在服务器上悄悄读取，并且绝对不要把这个 `.env` 文件公开传到网上。**

### 4\. 常用的现成云基建平台

**完全不用。** 现在个人开发者和小团队做全栈产品，基本不会自己去买裸金属云服务器从头折腾，而是直接组合使用几家现成的 **现代云基建平台（Serverless / BaaS，即后端即服务）** ——它们把最繁琐的服务器运维、数据库备份、账号认证和收款全都封装好了，而且绝大多数都提供非常慷慨的免费额度，初期做产品几乎零成本：

## 接入大模型的核心概念

现在假设我们要给刚才那个「写日记应用」加上 AI 功能——比如用户写完一篇日记后，点一下按钮，让 AI 自动帮他生成一段温暖的今日复盘总结，或者根据日记内容生成一张插画。

要在自己的应用里接入大模型能力，我们需要先搞懂下面这四个核心概念：

### 1\. 用 API 与 API Key 调模型

为什么我们做 AI 应用不需要自己买几十万的显卡去跑模型？因为各大模型厂商都已经把训练好的大模型跑在他们的超级服务器上了，我们只需要通过 **`API`** 去调用它们的一小部分算力即可。

- **什么是 `API` 与 `API Key` ？** **`API` （应用程序接口）** 就是我们的后端程序和大模型厂商服务器之间沟通的桥梁（约定了怎么发消息过去、怎么把模型的回答拿回来）。而在发请求时，必须带上一串名叫 **`API Key` （接口密钥）** 的长字符串——它就像是你的实名会员卡兼扣费卡，模型厂商看到这个 `API Key` ，才知道这个请求是谁发来的，并从你充值的账户余额里扣除对应的费用。至于具体的调用代码，你也完全不用自己手写，直接把模型厂商官方文档里的请求示例复制给 AI Agent，它就会自动帮你把接口接通。
- **第一方厂商 vs API 聚合平台，以及 `模型 ID（Model ID）`** ： 获取 `API Key` 一般有两种渠道：一种是去 OpenAI、Anthropic（Claude）、Google（Gemini）、DeepSeek、Kimi 等 **第一方官方平台** 分别注册充值；但做真实的 AI 应用时，往往不是一家模型就能包打天下（比如有的地方需要高性价比的文本模型，有的地方需要速度极快的轻量模型，有的地方又需要能生成图片的模型，而像 Claude 官方本身就没有生图功能）。因此市面上也有很多 **API 聚合平台** （比如海外的 [OpenRouter](https://openrouter.ai/) 、国内的词元跳动等），只需要充值一个账号、拿一个 `API Key` ，就能在代码里通过传入不同的 **「模型 ID（Model ID，每个模型唯一的身份证号）」** ，灵活切换调用不同厂商的模型。
![在应用里通过 API 调用大模型、区分多模态与管理无状态上下文的机制](https://book.oiloil.org/assets/articles/ai-and-dev-core-concepts/04-ai-api-stateless-and-context-v1.svg)

在应用里通过 API 调用大模型、区分多模态与管理无状态上下文的机制

### 2\. 多模态、计费与上下文缓存

所谓 **「模态」** ，就是 AI 模型能够理解和生成的信息类型，最常见的有四种： **文本、图片、音频、视频** 。在选模型接入产品时，一定要看清它的 **输入模态** 和 **输出模态** ：

- **纯文本模型** ：只支持「输入文本 → 输出文本」；
- **多模态理解模型（输入多模态 → 输出文本）** ：比如现在的 `Claude` 、 `GPT` 、 `Gemini` 、 `Kimi K3` 等主流模型，你不仅可以给它发文字，还可以把用户日记里拍的一张照片、一段录音或视频发给它，它能看懂照片里画了什么、听懂录音的内容，然后输出一段文本总结；
- **多模态生成模型（输入文本/参考图 → 输出图片/音频/视频）** ：比如如果你想根据用户的日记内容自动生成一张每日配图，或者把日记总结用温柔的人声读出来，那就需要调用输出模态为「图像（Image）」或「音频（Audio）」的专用生成模型。

当我们实际打开 [OpenRouter](https://openrouter.ai/) 这类 API 聚合平台挑选模型时（下面以高性价比的 **`DeepSeek V4.1 Flash`** 模型详情页为例），你可以在一个页面上看清决定成本与体验的所有关键指标：

![OpenRouter 平台上 DeepSeek V4.1 Flash 的模型详情页：包含模型 ID、支持模态、上下文长度、输入与输出价格、缓存读取价格与 TPS 吞吐速度](https://book.oiloil.org/assets/articles/ai-and-dev-core-concepts/04b-openrouter-deepseek-v4-1-flash.webp)

1. **模型 ID 与上下文窗口** ：左上角标题下方的 `deepseek/deepseek-v4.1-flash` （旁带复制按钮）就是我们在代码里调用它时填写的唯一 `Model ID` ；下方卡片里的 `MODALITIES` 标明了它支持文本与图片输入、文本输出， `CONTEXT` 标明了它的上下文窗口上限是 `1.0M` （即 100 万 Token）。
2. **输入价格（Input）vs 输出价格（Output）** ：在所有 API 平台上，模型 **「读进去的字（Input）」和「生成吐出来的字（Output）」是分开算钱的，而且输出价格往往比输入贵好几倍** 。比如看图中下方供应商列表的第一行，每 100 万 Token 的输入价格（ `Input /M` ）只要 **`$0.045`** ，而输出价格（ `Output /M` ）是 **`$0.50`** 。像 `DeepSeek` 系列模型之所以在开发者里极受欢迎，就是因为它的 API 价格比海外顶尖旗舰模型便宜了十几倍，非常适合在应用里承接高频的文本与代码执行任务。
3. **上下文缓存（ `Cache read` / Prompt Caching）** ：仔细看图中价格表里还有一列 **`Cache read /M` （仅需 `$0.006` ，比正常输入价格又便宜了近 8 倍）** 。这是什么意思？马上结合下一小节的「模型无状态」你就能彻底明白它的省钱威力。

### 3\. 模型的无状态特性

**「大模型本身是无状态的」** ——这是开发 AI 应用时最关键、也最容易颠覆新手直觉的一个概念。

平时我们在聊天软件里跟 AI 对话，比如第一句告诉它「我叫欧呦，今天写了一篇关于做网站的日记」，第二句问它「我刚才说我叫什么？」，它能准确答出「你叫欧呦」。这会让我们误以为模型服务器在脑子里记住了我们之前聊过的话。

但实际上， **大模型本身没有任何长期记忆，每次收到请求时它都是完全「失忆」的** （底层原理可以延伸阅读站内的 [《大模型底层原理：注意力机制与 KV Cache》](https://book.oiloil.org/articles/llm-attention-and-kv-cache) ）。它之所以能回答出你的名字，是因为在第 2 次发请求问「我叫什么」的时候， **我们的程序把第 1 轮你说的话、第 1 轮它回答的话，连同第 2 轮的新问题，全部打包在一起重新发给了大模型！**

理解了这一点，你就会明白两件事：

- 第一，当我们自己开发一个带连续对话功能的 AI 应用时，模型厂商是不会替你存聊天记录的——所有的历史状态都必须由我们自己的程序负责保存，并在每次请求时重新发给模型；
- 第二，正因为每次请求都要重发前面的内容，刚才在 OpenRouter 图里看到的 **「上下文缓存（ `Cache read` ）」** 才如此重要： **只要我们每一轮发送的系统提示词（ `System Prompt` ）和前面的历史消息固定不变，且两次请求间隔比较短，模型厂商检测到前面的内容一模一样，就会直接走上下文缓存** ，不仅省去了重新计算的时间，输入价格也会直接打一到两折。

### 4\. 上下文压缩与外部检索

既然每次请求都要把背景信息打包发给模型，那么 **单次请求发送给大模型的所有信息总和，就叫做「上下文（Context）」** 。在实际调用模型 API 的代码里，上下文通常由一个名叫 `messages` 的消息列表组成，里面最核心的就是两部分：

1. **`System Prompt` （系统提示词）** ：放在整个上下文最顶部的特殊指令，用来规定大模型的角色人设、任务边界和输出规则（比如在我们的写日记应用里， `system prompt` 就是：「你是一位温和敏锐的心理陪伴助手，请根据用户今天的日记内容，提炼出今日情绪关键词并给出一句不超过 50 字的鼓励」）。
2. **历史与当前消息（ `user` 与 `assistant` ）** ：系统提示词下面，紧跟着用户之前发过的内容（标记为 `role: "user"` ）和 AI 之前的回复（标记为 `role: "assistant"` ），一轮接一轮往下追加。

围绕上下文的管理，做 AI 应用时有三个必懂的实战原则：

- **上下文不是越多越好，而是越精简越准（上下文工程）** ： 你可以拿查字典来类比：如果只给你一页只有几个字的纸，想找一个字一眼就能看到；如果给你一本厚厚的字典，在里面找同一个字受到的干扰就大得多。这对应模型的注意力机制——上下文越精简、越垂直、越准确，模型推理出好结果就越轻松。
- **超过窗口上限时的「上下文压缩」** ： 上下文不是无限大的，不同模型有各自的窗口上限（比如 Codex 里的窗口大约在 25 万字左右，目前很多新模型达到了 100 万）。我们发送的消息和模型响应的消息都会计入历史，一旦超过上限没法再追加信息时，就会触发 **「上下文压缩」** ：把之前的对话信息做一个浓缩总结（比如把 25 万字摘要成 2 万字，大致描述之前做了哪些事情）。但这里必须注意： **一些重要的精确信息绝对不能被模糊压缩（比如明确的数字、ID）** ，因为一旦压缩失真，对后续对话的准确性影响非常大。
- **有海量历史资料怎么办？了解 `RAG` 与现在的「Agent 实时搜索」趋势** ： 如果用户在日记应用里已经写了上千篇日记，或者你的应用里有几百份文档，不可能每次请求都全塞进上下文里。过去很多教程会教你搭一套 **`RAG` （检索增强生成）** ——也就是提前把所有文档切碎、转换成数学向量建好索引库，提问时先去索引库里匹配。 **但现在很多最新的工程实践已经不再用传统 `RAG` 建索引的方式了，而是直接让 Agent 实时去搜索文件** （比如我们平时用的 AI Agent，就是直接通过关键词实时去搜索代码和文档文件的）。相比维护一套笨重的向量索引，让 AI 直接用关键词实时搜索并按需读取对应片段，往往更简单也更准确。

### 5\. 让 Agent 帮你调通 API

把上面这些概念串起来，我们在代码里向大模型发出的 **一次完整请求** ，实际长下面这个样子（你可以一眼看清请求地址 `URL` 、 `API Key` 、 `model` 模型 ID、 `messages` 上下文列表以及末尾的 `response_format` 是怎么组合在一起的）：

```
curl https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer 你的_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "deepseek/deepseek-v4.1-flash",
    "messages": [
      {
        "role": "system",
        "content": "你是一位温和的日记复盘助手，请按指定的 JSON 格式返回今日心情评分、标签与寄语。"
      },
      {
        "role": "user",
        "content": "今天把前后端和 AI API 的概念全部理清楚了，感觉很有成就感！"
      }
    ],
    "response_format": { "type": "json_object" }
  }'
```

**最关键的实战技巧来了：上面这段请求代码，现在根本不需要我们自己手写！**

在日常跟 AI Agent 对话开发产品时，让它去调试一个外部 API 非常简单： **你只需要去 API 平台的文档里复制一下请求路径（URL）和请求示例，甚至在本地开发调试时可以直接把 `API Key` 和 `URL` 发给 AI Agent，让它先在终端里自己发请求测试。** 等 Agent 自己在命令行里跑通、确认模型能正常返回响应之后，你再告诉它：「把这个接口接到我们日记应用的『生成今日复盘』按钮上，记得把 API Key 存进 `.env` 文件里」，它就会全自动帮你把前后端逻辑接好。

## 决定 AI 体验的三个细节

把大模型 API 接通之后，为什么有的 AI 产品用起来干脆利落、排版漂亮，有的却让人等得焦急、甚至页面渲染经常报错？这往往取决于最后这三个工程细节：

### 1\. 模型的输出速度：TPS（Tokens Per Second）

在挑选模型时，除了看模型聪不聪明、价格贵不贵，还有一个直接决定用户体验的核心指标叫做 **`TPS` （Tokens Per Second，即模型每秒钟能吐出多少个 Token/字）** 。

有的模型响应起来噼里啪啦一秒钟刷出一大片字，有的模型却像挤牙膏一样半天蹦出几个字，这就是 `TPS` 的差距：

- 目前大多数常规主力模型的 `TPS` 在 **40–60** 左右；
- 超过 **60** 就算比较快的水平，而一些专门针对速度优化的轻量模型（比如带有 `Flash` 、 `Mini` 后缀的模型）， `TPS` 可以达到 **80–100 以上** ，吐字速度比慢模型快出一倍多。

需要注意的是， **并不是越贵、推理能力越强的旗舰模型 `TPS` 就越高** ——恰恰相反，最庞大的旗舰模型往往吐字偏慢，反而是轻量级模型速度飞快。在我们的「写日记应用」里，如果用户点一下「生成今日心情标签」需要干等一分钟才能看到结果，哪怕写得再深刻用户也会失去耐心关掉页面；换成高 `TPS` 的模型 3 秒钟就把结果渲染出来，整个产品的交互手感就会好上太多。

![大模型输出速度 TPS（每秒生成 Token 数）决定用户交互体感](https://book.oiloil.org/assets/articles/ai-and-dev-core-concepts/05a-tps-output-speed-v1.svg)

大模型输出速度 TPS（每秒生成 Token 数）决定用户交互体感

### 2\. 结构化输出（JSON 格式）：让程序能把回答渲染成漂亮界面

平时我们在聊天框里跟 AI 对话，它返回的是一整段自由发挥的纯文本字符串（比如：「今天你过得很充实，心情是开心的，建议明天早点休息」）。

但在一个真正的产品界面里，我们往往不希望只展示一坨干巴巴的聊天文字，而是希望把「心情指数」渲染成一个彩色进度条，把「情绪标签」渲染成三枚漂亮的小徽章，把「今日寄语」放进专门的引言卡片里。如果 AI 每次返回的文字格式都不固定，前端程序根本不知道哪句话是标签、哪句话是寄语，就没法把它们拆分放进对应的 UI 组件里。

为了解决这个问题，我们就需要让大模型返回 **「结构化数据」——最通用的标准格式就是 `JSON`** （一种用花括号 `{}` 和 `字段名: 具体内容` 把数据分门别类装好的固定格式，就像一张填好的电子表单）。比如我们要求模型按下面的 `JSON` 结构返回：

```
{
  "moodScore": 85,
  "tags": ["专注开发", "攻克难题", "充实"],
  "summary": "今天顺利理清了前后端的核心概念，离做出自己的第一个完整产品又近了一步。"
}
```

现在绝大多数主流模型 API 都支持直接传入一个格式约束参数（比如 `response_format: { type: "json_object" }` ，或者直接传入一份规定好字段名和数据类型的模板，叫 `JSON Schema` ），强制模型严格按照我们规定的字段返回 `JSON` 。前端程序拿到这份规整的数据后，就能稳稳当当地把分数、标签和寄语分别填进漂亮的页面组件里了。

![让大模型返回 JSON 结构化数据以渲染前端 UI 组件](https://book.oiloil.org/assets/articles/ai-and-dev-core-concepts/05b-json-structured-output-v1.svg)

让大模型返回 JSON 结构化数据以渲染前端 UI 组件

### 3\. 流式响应与 JSON 的取舍

最后还有一个大家每天都在体验的概念，叫做 **「流式响应（Streaming）」** 。

在调用大模型 API 时，只需要把参数里的 `stream` 设为 `true` ，就能开启流式响应：

- **不开启流式响应（ `stream: false` ）** ：大模型必须在后台把整篇几百字的回答全部想完、写完，才一次性打包返回给前端。在这几秒到十几秒的时间里，用户在页面上只能盯着转圈圈的加载图标干等；
- **开启流式响应（ `stream: true` ）** ：大模型每推理出一个字，就立刻通过网络把这一个字推送给前端显示出来——也就是大家平时在 ChatGPT 或 Codex 里看到的「像打字机一样一个字一个字往外蹦」的效果。哪怕总耗时一样，用户第 1 秒就能开始阅读开头的内容，等待焦虑感会大大降低。

**但这里有一个非常关键的实战避坑点：当你的功能既需要返回 `JSON` 结构化数据，又想开启 `Streaming` 流式响应时，两者会产生直接冲突！**

为什么会冲突？因为完整的 `JSON` 必须有头有尾（左右花括号 `{ ... }` 和双引号必须严丝合缝配对）才能被程序正常解析。如果开启了流式响应，第 1 秒钟前端只收到了前半截残缺的字符串（比如 `{"moodScore": 85, "tags": ["专注` ），这时候后面还没吐出来，它根本不是一个合法的 `JSON` ，前端程序直接拿去解析渲染就会当场报错。

因此在日常开发 AI 功能时，我给大家的取舍建议非常明确：

1. **如果是长文对话、写文章、写日记总结这类纯文本展示场景** ：果断开启 **流式响应（ `stream: true` ）** ，让文字实时蹦出来，保障丝滑的阅读体验；
2. **如果是提取标签、打分、生成结构化卡片这类需要 `JSON` 渲染 UI 的场景** ：默认 **不要开启流式响应** ，优先搭配一个高 `TPS` 的快速模型，等模型在一两秒内把完整的 `JSON` 生成完一次性返回后再渲染到页面上（除非你专门让 AI 写了一套「边接收半截数据、边自动补全括号」的复杂解析逻辑）。
![流式响应（Streaming）逐字实时输出与 JSON 格式的取舍](https://book.oiloil.org/assets/articles/ai-and-dev-core-concepts/05c-streaming-response-v1.svg)
