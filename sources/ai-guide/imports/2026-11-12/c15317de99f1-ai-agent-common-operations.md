## AI Agent 能帮我们干什么

很多刚接触 Vibe Coding 的朋友，平时已经习惯了在网页版 ChatGPT、Claude 或 DeepSeek 的聊天框里问问题。如果直接把那套习惯搬过来，往往会好奇：我们装在电脑上的 AI Agent 客户端，跟网页聊天框到底有什么不一样？

最核心的区别在于： **网页版聊天框只能「一问一答」给你返回一段文字，而 AI Agent 是真正能在你的电脑上动手干活的。**

![AI Agent 的三项核心能力：直接读写本地文件、自动执行命令与调用内置工具](https://book.oiloil.org/assets/articles/ai-agent-common-operations/05-agent-three-core-capabilities-v1.svg)

AI Agent 的三项核心能力：直接读写本地文件、自动执行命令与调用内置工具

具体来说，当你向 AI Agent 交代一项任务时，它手头有几项最核心的执行能力：

1. **直接读写和管理本地文件** ：它不需要你手动把代码或文章复制粘贴进对话框，而是可以直接在你电脑的文件夹里查看已有文件、新建文档或修改代码。
2. **自动执行命令并根据结果继续行动** ：它可以自己调用电脑的终端（也就是电脑自带的命令窗口——过去程序员要在里面敲指令来安装软件、启动网页预览或运行脚本，现在这些指令全都可以由 AI 替你输入和执行）。更重要的是，如果它跑完命令发现报错了，不需要等你把报错复制给它，它自己看到运行结果后就会接着思考下一步怎么修，直到把问题解决。
3. **调用各类内置工具辅助干活** ：除了读写文件和跑命令，它还可以直接调用联网搜索去查最新资料、调用图片生成模型做配图，或者在需求不明确时主动向你发起提问。

理解了 AI Agent **「会自己读写本地文件、会自己执行命令」** 这两个基本动作，你就能非常自然地明白接下来我们要讲的所有日常操作——为什么干活前必须先用独立文件夹划定它的读写范围、为什么要用方便它读写的文档格式，以及为什么要给它开放执行命令的最高权限。

## 先给项目建独立文件夹

打开任何一款 AI Agent 客户端，左侧栏最核心的入口都是「项目（Project）」。项目其实非常简单，就是 **我们电脑上对应的一个文件夹** 。

### 1\. 为什么需要单独文件夹

之所以需要专门建一个文件夹，是因为我们做一件事的所有东西都要统一放在一起，相当于做一个分类。

当我们创建一个项目之后，AI 在执行各种操作时，会把这个文件夹当作一个 **本地知识库** 。我们的历史上下文（所谓「上下文 Context」，就是 AI 在当前对话里能记住和参考的信息容量，相当于它的短期工作记忆），就会以文件的形式长期保存在这个文件夹里——这里面不仅有真正让 AI 去写的代码，还有我们的设计规范、技术架构设计、工作流等文档。哪怕下次新开一个对话，AI 只要读取文件夹里的内容，就能立刻知道这个项目之前做到了哪里。

### 2\. 不要拿桌面当项目目录

不少新手刚开始用的时候图省事，没有提前创建一个单独的项目文件夹，而是直接选择电脑的「桌面」作为项目目录。

这样做会有两个明显的麻烦：第一，下次我们再打开软件让 AI 改代码的时候，还得专门告诉它「你需要去桌面上的哪一个文件夹里面进行文件编辑」，沟通起来非常繁琐；第二，AI 在桌面这个大目录里搜索文件时，也很容易搜到桌面上的其他无关目录里去，结果做错事情、改乱别的文件。

所以每次开始做一个新作品或新任务前，第一步永远是在电脑上新建一个独立的空文件夹，再在 AI Agent 里打开这个文件夹作为项目。

![桌面混放文件容易串目录与独立项目文件夹作为本地知识库的对比](https://book.oiloil.org/assets/articles/ai-agent-common-operations/01-desktop-chaos-vs-project-folder-v1.svg)

## 认识 Markdown 与 HTML

刚建好项目文件夹准备往里面存资料或让 AI 写方案时，很多朋友按照平时的办公习惯，第一反应往往是往里面塞一个 **Word 文档（`.docx` ）** 。

但在 AI 编程与 Agent 协作时代，我们几乎不会使用 Word，文件夹里最主流、每天打交道最多的永远是另外两种文件：以 `.md` 结尾的 **Markdown** 和以 `.html` 结尾的 **HTML** 。在这两种格式里，大家只需要先记住它们最核心的分工： **Markdown 是适合 AI 和人之间交互的，而 HTML 是适合给人看效果的。**

### 1\. 为什么不选 Word 文档

Word 是做给人类在图形界面里排版打印用的，它的底层并不是一份干净的纯文本，而是把文字、字体样式和排版信息打包压缩成了一个复杂的封装容器。

对 AI Agent 来说，它没办法像看普通文本那样直接「一眼看清」Word 文件的源码，每次读取或修改都必须先调用额外的转换工具去拆包解析，不仅麻烦、容易丢失排版格式，还会白白浪费上下文记忆空间。

而 **Markdown（`.md` ）** 和 **HTML（`.html` ）** 本质上都是完全公开透明的纯文本源码——你随便用电脑自带的记事本就能直接打开看到里面的每一个字符，AI 读写起来没有任何阻碍。

![AI 时代主流的 Markdown 与 HTML 分工及为什么不用 Word](https://book.oiloil.org/assets/articles/ai-agent-common-operations/04-markdown-vs-html-roles-v1.svg)

AI 时代主流的 Markdown 与 HTML 分工及为什么不用 Word

### 2\. Markdown：人机交互格式

Markdown 过去是程序员写技术博客常用的轻量文本格式：在文字前面加一个井号 `#` 就代表大标题，加两个井号 `##` 代表二级标题，加一个横杠 `-` 就代表无序列表。哪怕我们不主动要求，AI Agent 默认写出来的方案和文档也全部是 Markdown 格式。

![Markdown 源文件语法与渲染后的文档效果可视化对比](https://book.oiloil.org/assets/articles/ai-agent-common-operations/06-markdown-syntax-vs-render-v1.svg)

Markdown 源文件语法与渲染后的文档效果可视化对比

为什么它最适合用来和 AI 交互？相比 Word 文档或网页代码，Markdown 有三个很大的好处：

1. **源码直接可读** ：就算在没有排版渲染的环境里直接打开源文件，我们看到里面的井号 `#` 和横杠 `-` 也能一眼看清文档的层级结构。
2. **极其节省 Token、生成速度快** ：这里的 **Token** 可以简单理解为 AI 阅读和生成文字时的计费与容量单位——字数越少、符号越精炼，消耗的 Token 就越少。在 Markdown 里表示一个大标题只需要敲一个 `#` 号，没有冗长的样式代码，因此 AI 读写的效率最高、占用的上下文记忆空间也最少。
3. **容错率高、方便修改** ：Markdown 中间哪怕某一个符号写错了，也完全不影响其他段落的正常阅读和渲染。

因此在日常协作中，无论是让 AI 先写一份产品需求方案（PRD）、沉淀项目里的设计规范与工作流，还是后面要讲到的跨话题交接文档， **凡是用来在人和 AI 之间传递信息、对齐思路、反复修改的文档，都应该用 Markdown。**

### 3\. HTML：可视化网页格式

HTML 则是标准的网页格式，通过一层层嵌套的标签（比如 `<div class="card">` 、 `<button>` ）、CSS 样式和脚本，放到浏览器里就能直接渲染成带颜色、多栏排版、图表甚至可点击按钮的可视化页面。

![HTML 源文件标签语法与浏览器渲染后的网页交互效果可视化对比](https://book.oiloil.org/assets/articles/ai-agent-common-operations/07-html-syntax-vs-render-v1.svg)

当我们需要看页面的真实配色、横向网格布局、交互动画，或者想做一个带选项按钮的风格预览页时，Markdown 这种垂直线性的纯文本就无能为力了，这时候就适合让 AI 生成 HTML，直接在浏览器里打开看效果。

但为什么我们不在日常所有沟通里都让 AI 生成 HTML 呢？因为直接让 AI 写 HTML 有两个明显的成本：

- **Token 开销大、生成速度慢** ：为了呈现出好看的样式，AI 往往要先写几百行 CSS 样式和标签结构，生成一份 HTML 消耗的 Token 通常是同等内容 Markdown 的两到四倍，等待时间也慢得多。
- **结构容错率低，不适合频繁改文字** ：HTML 对标签闭合的要求非常严格（有开头 `<tag>` 就必须有配对的结尾 `</tag>` ），一个七八百行的 HTML 文件，只要后半段某一个标签写错，整个页面在浏览器里就可能渲染不出来；而且把大量样式代码塞进对话里，后续让 AI 排查和修改起来也会占用很多上下文。

所以最顺手的配合方式是： **前期和 AI 讨论方案、记笔记、存规范，全部用轻量省钱的 Markdown；等方案定下来、真正需要看视觉样式和交互效果时，再让 AI 生成 HTML 放进浏览器里看效果。** （顺带提一句，单文件 HTML 适合承载比较轻量的网页或演示原型；等后面做规模更大的完整网站时，由于单文件代码会太长，我们通常会用前端框架——也就是把复杂网页拆成多个小模块文件分开管理的开发工具——来组织代码，不过最终打包出来给浏览器看的产物依然是 HTML。）

## 动手前的三个基础设置

选好项目文件夹之后，在正式发消息之前，对话框底部工具栏和软件设置里有三个基础开关，建议大家在动手前先调好：

### 1\. 权限档位开最高权限

默认情况下，AI Agent 每次想要修改本地文件或者在终端里执行一条命令时，软件出于安全保护都会停下来弹窗问你「允不允许执行」。为了控制它需要问你的频率，输入框底部通常会提供不同的权限档位——比如每步操作都手动批准、仅敏感操作批准，或者最高权限 **`Full Access` （完全访问权限）** （如果你习惯在终端命令行里使用 Claude Code，则可以在启动时输入 `claude --dangerously-skip-permissions` 跳过权限询问）。

**我认为每一次都直接给最高权限就好了。** 因为现在的 AI 已经有很强的连续执行能力，如果你不给它最高权限，它在干活的过程中每改一个文件、每跑一条命令都会频繁停下来问你权限问题，不仅打断节奏，整体效率也会非常低下。

而且大家不用过度担心安全问题——现在的 AI 在遇到真正敏感的操作时（比如要不要删除某些重要文件），即便你开了最高权限，它通常也会先停下来问你一下。

### 2\. 思考档位开 High 或 Max

输入框底部的工具栏里一般还会有 **思考档位（Reasoning / Effort）** 的选择。

很多新手第一次看到这个选项会好奇： **「思考档位」到底对应的是什么意思？**

其实现在的 AI 模型在真正开口回答或动手改代码之前，会像人做难题先在草稿纸上推演一样，有一段 **内部思考过程** ——它会先在脑子里想清楚这件事情要分几步做、需要先看哪些文件、可能会踩什么坑，把思路理顺之后再去动手。而「思考档位」控制的就是 **允许 AI 在动手前花多少时间和精力去推演打草稿** ：

- 当档位设得比较低（如 `low` ）时，AI 几乎不打草稿就直接动手，反应速度最快，但遇到稍微复杂一点的需求就容易考虑不周、顾此失彼；
- 当档位调高（如 `high` 或 `max` / `extra high` ）时，AI 在动手前会花更多时间把上下文和各种边界情况反复推演清楚，虽然每次等待的时间会多几秒钟，但做出来的东西一次性成功率高得多。

不同模型和客户端里的档位叫法略有不同（通常分为 `low` 、 `medium` 、 `high` 、 `max` 或 `extra high` ，在命令行工具里也可以输入 `/effort` 切换）。一般来说，我平时都是直接开到 **`high`** 或者 **`max`** 的。 **我建议新手朋友也直接开到和我差不多的程度就好了** ，这样能保证 AI 在动手前想得更周全，减少低级返工。

![将思考档位（Reasoning Effort）调至 High 或 Max 先推演再动手](https://book.oiloil.org/assets/articles/ai-agent-common-operations/08b-high-reasoning-effort-v1.svg)

将思考档位（Reasoning Effort）调至 High 或 Max 先推演再动手

### 3\. 开启运行期间防休眠

当我们交代了一个比较复杂的任务、需要让 AI Agent 自己在后台跑比较长的时间时，建议顺手在软件的通用设置（General）里把 **「运行期间防止电脑休眠（Prevent sleep while running）」** 打开。这样哪怕你中途离开座位去忙别的事，也不会因为电脑自动锁屏休眠而把正在执行的任务断掉。

![开启运行期间防止电脑休眠保障后台长任务不断线](https://book.oiloil.org/assets/articles/ai-agent-common-operations/08c-prevent-sleep-v1.svg)

## 怎么交代任务与引用文件

配好基础开关后，接下来就是往对话框里发消息交代任务了。这里有三个新手最常问到的操作问题：什么时候该用 `Plan` 模式、怎么一句话让 AI 听懂我们的想法，以及现在还需不需要用 `@` 去指定文件。

### 1\. 什么时候开 Plan 模式

主流的 AI Agent 在输入框底部工具栏里都提供了 **Plan 模式** 开关（开启后 AI 不会一上来就直接改代码，而是先帮你梳理出一份实施方案）。

我平时并不是所有对话都开 Plan 模式， **一般只有在实现一些比较复杂的功能、第一次从零开发一个项目，或者做一个特别大的功能时，我才会开启 Plan 模式。**

因为面对这类大任务，我需要先确认它在后续比较长的一段时间里到底打算做哪些事情，看一下它的规划和我想的会不会有偏差；而且在看它制定方案的过程中，我自己也能顺便学习一下它是怎么拆解和设计的。如果是平时很简单的小修改，直接在默认模式下让它动手改就可以了。

### 2\. 让 AI 主动反问自己

很多刚接触 Vibe Coding 的朋友，面对空白输入框时总觉得要把需求写得像长篇论文一样才行。其实正如我们在 [《我使用 AI 的四个高效习惯》](https://book.oiloil.org/articles/ai-efficiency-habits) 里聊到的， **想要快速让 AI 了解我们的想法，最有效的办法就是让它来问我们问题。**

比如你在开始做一个新功能或新网站时，可以在开启 Plan 模式后直接对它说：

> 我想做一个【你的想法】，为了把它做好，你需要我的什么信息？请先向我提问。

**之所以要主动告诉它来反问我们，是因为它能够基于我们提出的目标，自己去挖掘它还没有搞清楚的地方。** 在 Plan 模式下，像 Codex 这类工具还会直接把问题整理成带推荐选项的表单卡片，你只需要顺着它的提问一题题勾选或用语音简短回答，很快就能把所有细节对齐清楚。

![开启 Plan 模式并让 AI 主动反问以对齐复杂功能方案](https://book.oiloil.org/assets/articles/ai-agent-common-operations/02-plan-mode-and-ask-back-v1.svg)

开启 Plan 模式并让 AI 主动反问以对齐复杂功能方案

### 3\. @ 引用文件与直接贴图

在很多早期的教程里，大家都会教新手在输入框里敲 `@` 符号来选中项目里的某一个具体文件。

但说实话， **`@` 具体文件的做法现在用的人已经越来越少了** ，大家日常更多是通过 `/` 或 `@` 去调用封装好的 [Skill（也就是提前把经验规范与脚本打包好的技能文件夹，我们会在后续章节详细讲）](https://book.oiloil.org/articles/skill-guide) 。

原因很简单：以前我们手动 `@` 具体文件，是为了帮 AI 快速定位代码位置、节省它自己搜索文件消耗的上下文和 Token 开支；但现在 AI 的能力越来越强了，它完全能够根据我们的自然语言描述，自己非常准确地去找到对应的文件。而且现在很多做 Vibe Coding 的开发者，连自己项目文件夹里具体有哪些代码文件都不太清楚了，所以 `@` 文件这个方法就算你不了解也完全没关系。

只有当我们 **非常明确地知道要让它参考某一个特定文件（比如某份写好的设计规范文档），或者明确指定只修改某一个文件** 时，顺手在对话框里 `@` 一下那个文件即可。

## 运行中的操控与撤回

把任务发出去之后，AI Agent 往往会自己在后台连续跑上好几分钟。在它干活的过程中，有几项日常高频的操作姿势可以帮你随时掌控节奏：

### 1\. 消息排队与立即打断

当 AI 正在执行任务还没停下来时，如果你又想到了下一步要做的事情，直接在输入框里发出去就行——新消息默认会进入 **排队（Queue）** 状态，等它干完手头这一步就会自动接着处理。

如果你看着它的执行过程，发现它方向走偏了、想要马上叫停纠正，直接点击输入框旁的插入/打断按钮（如 Codex 里的 `Steer` 按钮或停止按钮），就能立刻把纠正指令插进去。

![运行中发送新消息默认排队（Queue）与点击 Steer 立即打断纠偏](https://book.oiloil.org/assets/articles/ai-agent-common-operations/09a-queue-and-steer-interrupt-v1.svg)

运行中发送新消息默认排队（Queue）与点击 Steer 立即打断纠偏

### 2\. 支线提问 /btw 与 /side

有时候主对话正在专心开发一个功能，你突然冒出一个临时的支线小问题，或者顺眼看到页面上有个很简单的小交互想顺手改一下。如果直接发进主对话，既会打断主线，又会污染主对话的上下文。这时候可以用两个专门的斜杠命令：

- **`/btw` 命令** （在 Claude Code 等工具中使用）：输入 `/btw` 加上你的问题，可以用来做临时的支线提问。AI 会基于当前上下文快速回答你，但这次问答不会写进主对话的历史记录里。
- **`/side` 命令** （在 Codex 中开启右侧边栏会话）：在输入框敲 `/side` 会在界面右侧单独打开一个侧边栏对话，它会 **自动继承当前左侧主对话的所有上下文信息** 。你不仅可以在右侧问支线问题，还可以在右侧并行做一些轻量修改——比如说主线程正在跑任务，我当时突然想到一个很简单的交互修改，就可以直接在 `/side` 里面让它改掉。唯一需要注意的是， **`/side` 里面是临时会话，时间一到它就会自己过期** （过期只是指右侧这个临时聊天窗口不能再继续发消息，它刚才已经帮你写进本地文件里的代码修改依然会完好保留），所以我们不要在那里面做太重的操作。
![使用 /btw 支线提问与 /side 开启右侧边栏并行临时会话](https://book.oiloil.org/assets/articles/ai-agent-common-operations/09b-btw-and-side-session-v1.svg)

使用 /btw 支线提问与 /side 开启右侧边栏并行临时会话

### 3\. 改坏了文件怎么撤回？

很多新手会问：如果 AI 这一轮改完代码，我发现效果不对甚至把原本正常的页面改坏了，怎么撤回？

需要注意， **现在很多主流的 AI Agent 已经不包含内置的文件撤回操作了。** 所以防止改坏、随时撤回最好的方式，就是使用 **Git** （程序员最常用的代码版本管理工具，相当于给项目文件夹装了一个「随时存档、随时读档回退」的时间机器）来管理我们的项目——每做完一个满意的小阶段就让 AI 存个档，万一后面改乱了，一句话就能完整退回上一版。关于 Git 的具体用法，我们在后面的《从 0 到 1 学会使用 Git 与 GitHub》一章里会有单独的完整教程。

## 上下文管理与跨话题交接

当我们在同一个话题（也就是左侧列表里的一条独立对话）里跟 AI 连续聊上十几轮之后，你会注意到输入框角落的上下文（Context）进度圆环或百分比数字在不断往上涨。

### 1\. 哪些内容会占用上下文？

**上下文其实就是我们跟 AI 对话的所有内容，再加上它调用工具、自己去读取的文档、执行的终端命令，包括它去查看图片——这些所有信息都会占用它的上下文。**

每个模型的上下文窗口都有上限。当上下文的长度达到比如 **90%** 左右的时候，AI 一般来说就会自动触发自己的 **上下文压缩** （也就是把前面很长的对话历史浓缩成一份精简摘要，腾出空间继续往下聊，你也可以敲 `/compact` 手动触发压缩）。不过压缩之后难免会丢失一部分细节，而且上下文塞得越满，AI 的指令遵循能力就越容易下降。

### 2\. 跨话题交接的三种方式

因此，当一个阶段性任务做完、上下文快满的时候，或者当我们想把当前项目交给另外一个 AI Agent 接着做的时候，通常需要新开一个话题。为了让新话题里的 AI 知道前面干了什么，一般来说有三种交接方式：

1. **让它写一份 Handoff（交接）文档** ：这是最通用、最稳妥的做法。在关掉旧话题前，先对当前 Agent 说一句：「 **请把我们目前做完的事情、修改过的文件和接下来要做的事，整理成一份 `handoff.md` 交付文档保存在项目里。** 」然后你新开一个话题（或者切换到另一个品牌的 AI Agent 里面），只需要让它先读一下这份 `handoff.md` 文件，它就立刻清楚前面的所有进度了。
2. **Fork（分支）当前话题** ：如果下一个任务高度依赖刚才的完整上下文，很多客户端支持在对话右上角菜单、左侧话题列表右键或通过 `/fork` 命令对当前话题执行 **Fork（分支）** 操作。Fork 出来的新话题会完整保留当前节点之前的所有上下文，你可以直接在这个分支上往另一个方向继续探索。
3. **在新话题里 `@` 另一个话题** ：在类似于 Codex 这种产品里面，当我们新开一个干净的话题时，可以直接在输入框里敲 `@` 并输入之前话题的标题关键字，选中 **之前的另外一个话题** 。这时候它就会自动拿到一份精简后的旧话题上下文，既知道背景，又不会把旧话题里冗长的过程信息全背过来。
![上下文达到 90% 自动压缩与跨话题交接的三种方式](https://book.oiloil.org/assets/articles/ai-agent-common-operations/03-context-handoff-three-ways-v1.svg)

## 联网调研与生成图片

最后，除了读写本地代码和执行终端命令，现在的 AI Agent 还自带了两项非常实用的内置能力，平时做网站或整理资料时直接开口就能调动：

### 1\. 联网调研（Web Search）

当你在做项目前需要查最新的技术文档、了解某个领域的背景，或者收集自己的公开资料来建个人网站时，可以直接对 Agent 说：

> 使用联网调研工具，帮我搜索一下【主题或名字】的相关信息，并整理到项目文档里。

Agent 会像人用搜索引擎一样，先搜索关键词，再根据搜出来的结果派生新的关键词一步步深挖，把公开网页、GitHub、技术社区里的信息汇总起来。调研完成后，回复底部通常会附上参考来源（ `Source` ）链接，我们可以点开确认信息确实出自那里，避免 AI 出现瞎编的幻觉。

### 2\. 生成图片与绿幕抠图

平时我们在 Vibe Coding 做网页、做游戏或者做卡片时，经常需要定制化的插画或图标。有些 AI Agent 是内置了图片生成功能的，它们会在后台调用外部的图片生成模型来帮我们生成图片（比如在 Codex 里内置了 `/imagegen` 命令，但在其他 Agent 里叫法或触发方式可能不同）。

因此平时使用时，我们 **不用专门去记或主动触发某个斜杠命令，一般来说直接用自然语言让它去生成图片，或者先问它一句「你有没有图片生成工具」就好了** ——只要它内置了生图能力或装了对应的生图工具，它就会自己编写提示词、调用生图模型把图片生成到本地项目文件夹里，并自动写进网页代码中。

这里顺便分享一个做好看网页很常用的生图小技巧：由于不少生图模型没办法直接原生生成透明背景的 PNG 图片，如果你直接让它生图贴到网页上，图片四周往往会带着一块突兀的白色或杂色方框。

遇到这种情况，可以直接在对话里把「绿幕背景 + 脚本抠图」的要求告诉 Agent：

> 帮我生成一个手绘风格的小狗配图，请生成纯绿色背景（或纯灰底）的图片，生成后写一个脚本把背景颜色抠掉，转成透明底的 PNG。

就像影视拍摄里的绿幕抠像一样，AI 生成图片后会自己写几行脚本把主体干净地抠出来，放进网页里的视觉效果会精致很多。
