## 前言

哈喽大家好，我是欧呦，今天这篇文章是一个从 0 到 1 的 Git 与 GitHub 上手教程。在这篇文章里，我不仅会和大家分享它们的核心概念与常见命令，更会重点讲清楚它们到底能帮我们解决什么问题，以及平时跟 AI Agent 交互时，怎么直接用自然语言去指挥它操作。

很多刚开始接触 Vibe Coding 的朋友，在用 AI 写项目时经常会遇到这样的情况：前几轮让 AI 写出来的页面明明已经能正常跑了，结果下一轮让它加个新功能或者调个样式，AI 一下子改了十几个文件，页面直接报错白屏；这时候你想让它改回刚才正常的样子，它却越改越乱，最后只能推倒重来。也有朋友为了防备改坏，每改完一版就在桌面上手动复制粘贴一堆 `网站-v1` 、 `网站-最终版` 、 `网站-打死不改版` 的文件夹，过两天连自己都分不清哪个文件夹里装的是哪一版代码。

之所以会出现这些问题，是因为项目缺少一套版本管理机制。而在真实的软件开发里，所有开发者和 AI Agent 都在用同一套标准工具来管理代码版本，也就是 **Git** 和 **GitHub** 。在 AI Agent 时代，你完全不需要像以前那样死记硬背几十条枯燥的终端命令——只要搞懂底层是怎么运作的，平时跟 AI 说一句自然语言，它就能帮你把存档、撤回、建分支和同步云端全部处理好。

## 本地存档与版本回滚

在正式上手操作之前，我们先在本地把版本管理跑通，搞清楚怎么给项目做阶段性存档、怎么在 AI 改坏代码时一键退回。

### 1\. Git 与 GitHub 区别

很多新手容易把 Git 和 GitHub 混为一谈，以为它们是同一个东西。其实它们一个是装在你自己电脑上的本地工具，一个是放在网上的云端平台：

![Git 本地存档与 GitHub 云端联机托管的核心区别](https://book.oiloil.org/assets/articles/git-from-scratch/01-git-vs-github-savegame-v1.svg)

Git 本地存档与 GitHub 云端联机托管的核心区别

#### Git：装在电脑本地的「单机游戏存档器」

**Git** 是一个运行在本地电脑上的软件，本质上是一个版本管理的命令行工具（命令行就是在电脑终端窗口里通过输入文字指令来操作软件的方式）。

版本管理有什么用呢？比如 AI 在我们的项目文件夹里修改代码，我们对文件每完成一次阶段性的修改，都可以用 Git 记录一个版本（比如 `V1 版本` 、 `V2 版本` ）。当后面某一次让 AI 修改代码，发现改出来的效果不好或者把项目改崩了，我们随时可以退回到之前的 `V1 版本` ——这就是版本管理最基础、也最常用的用途。

你可以把 Git 直接理解为 **单机游戏里的本地存档功能** ：打 Boss 之前存个档，之后不管是挂掉了还是通关了，你随时都能读档回到之前存档的位置；但如果你一直不存档，一旦挂掉了就只能从头重开了。

#### GitHub：放代码的「云端存档与多人联机平台」

如果我们只使用 Git，它只能在自己的电脑本地做版本管理——虽然自己写的代码更新之后可以随时回滚，但换了一台电脑，或者其他人想要获取你的代码一起改，还是拿不到的。

而 **GitHub** 就是一个云端的代码托管平台。通过 GitHub，我们可以把本地的代码仓库同步到云端，方便跨电脑拉取或者多人团队协作管理同一个项目。接着上面单机游戏的例子，GitHub 就相当于一个 **云端存档平台** ：假设你在自己家电脑上存了档，周末跑到朋友家电脑上还想接着玩之前的游戏进度，直接登录云端把存档拉下来就能继续玩。

这里有一个很重要的认知： **Git 和 GitHub 并不是死绑定的关系** 。除了 GitHub 之外，市面上还有很多其他的云端代码托管平台（比如 GitLab、Gitee 等；极端点说，你甚至拿个 U 盘把带 Git 记录的文件夹拷给朋友也能传代码，只是很不方便），只不过 GitHub 是目前全球最主流的托管与开源社区平台。

### 2\. 初始化、提交与回滚

搞清楚概念之后，我们来看看怎么在自己的项目里把 Git 用起来。现在最省心的方式，就是直接打开你常用的 AI Agent（比如 Codex、Claude Code 或 Cursor），用自然语言让它替你操作：

![用 AI Agent 初始化仓库、提交版本与一键回滚，并配合 Oil Git 可视化查看](https://book.oiloil.org/assets/articles/git-from-scratch/02-init-commit-rollback-v1.svg)

用 AI Agent 初始化仓库、提交版本与一键回滚，并配合 Oil Git 可视化查看

#### 第一步：安装 Git 与初始化项目仓库（Init）

如果你的电脑上还没装过 Git，最推荐的方式就是直接跟任何一个 AI Agent 说一句：

帮我安装一下 Git。

Git 安装好之后，有一点需要特别注意： **Git 并不会默认对你电脑里的每一个文件夹都做版本管理** ——毕竟平时放电影、照片的普通文件夹也没必要记版本，只有代码仓库或需要长期维护的项目，我们才去开启版本管理。

当我们新建了一个项目文件夹准备开始写代码时（关于为什么要一个项目建一个独立文件夹，可以参考第一章 [《了解 AI Agent 的常用操作》](https://book.oiloil.org/articles/ai-agent-common-operations) ），可以先跟 AI 说：

帮我初始化一下这个项目的 Git。

AI 会帮你执行初始化命令（ `git init` ）。初始化完成之后，如果你打开系统的「显示隐藏文件」，会看到项目根目录里多出了一个名叫 `.git` 的隐藏文件夹。这个 `.git` 文件夹里存放的就是当前项目所有的版本历史与 Git 配置信息，平时千万不要手动去删改它。

#### 第二步：保存文件 ≠ 生成版本，提交（Commit）才是存档

很多初学者会有一个误区：以为在编辑器里改完代码按下保存（或者 AI 帮我们改完文件），Git 就会自动每改一下生成一个新版本。

其实不是的—— **修改并保存文件，只是改了当前工作区里的内容，并不会自动生成版本记录。想要真正存下一个版本，必须执行一次「提交（Commit）」** 。

每当你让 AI 完成了一个小功能，在浏览器里看了一眼确认没问题，就可以像打游戏存盘一样跟 AI 说：

帮我提交一版代码。

AI 在帮你执行提交命令（比如 `git commit -m "完成首页首屏排版"` ）时，会自动根据刚才修改的内容写一句清晰的版本描述，把当前所有文件的状态正式打包存成一个新版本（如果是这台电脑第一次用 Git 提交，AI 可能会问一下你的名字和邮箱用来给存档留个署名，直接把昵称和常用邮箱告诉它即可）。

#### 第三步：查看当前状态、一键回滚与跨版本撤回

平时跟 AI 连续聊了十几轮之后，如果你记不清当前改了哪些文件、或者不确定刚才改的内容到底有没有提交过，可以随时让 AI 帮你查一下当前状态（对应 `git status` 和 `git diff` ）：

帮我看下现在在哪个分支，有哪些文件修改了还没提交。

只要你养成了阶段性提交（Commit）的习惯，后面再让 AI 大改代码时心里就完全有底了。假设你存好了 V1 版本，接着让 AI 尝试改一版新布局，结果改完发现效果不是自己想要的，甚至页面直接报错了，这时候不需要让 AI 在错代码上硬修，直接跟它说：

刚刚修改的效果不太好，帮我撤回到上一次提交的版本。

AI 就会直接把工作区里改乱的代码清理掉，让你回到上一次 Commit 时干净、正常的状态。

如果你已经连续提交了 V1、V2、V3 好几个版本，后来发现 V2 和 V3 的改动方向不对，想直接退回到更早之前的某一个版本，也可以让 AI 先列出历史提交记录（对应 `git log` ），再指定退回哪一版：

列出最近 5 次提交记录，帮我退回到还没改导航栏之前的那一版。

那如果坏代码不仅在本地提交了，还已经推送（Push）到了后面要讲的 GitHub 云端，还能撤回吗？同样可以——这时候直接告诉 AI：

刚才推上 GitHub 的那一版有问题，帮我生成一个撤销刚才改动的提交并重新推上去。

AI 会使用 `git revert` 帮你生成一次安全的「反向抵消提交」，既能把线上代码恢复原状，又不会破坏云端已有的历史记录。

#### 新手强烈推荐：搭配可视化工具 Oil Git 一起看

刚开始学 Git 的时候，如果你只对着 AI Agent 的聊天框操作，因为看不到 `.git` 里面到底存了几个版本、每次具体改了哪几行代码，脑子里很容易觉得抽象。

所以我非常建议刚入门的朋友，在电脑上顺手装一个我开源的桌面端 Git 可视化工具 **[Oil Git](https://git.oiloil.org/)** （开源仓库： [oil-oil/oil-git](https://github.com/oil-oil/oil-git) ）。你可以一边在 AI Agent 里用自然语言做提交、建分支，一边打开 Oil Git 对照着看：每次 AI 提交完一版代码，Oil Git 的时间线上是怎么多出一个版本节点的、每个版本里具体新增或删掉了哪几行代码（甚至图片改前改后的滑动对比），一眼就能看明白。

## 分支开发与冲突处理

只用一条时间线做存档和回滚，应付简单的单线修改已经够用了。但当我们想同时推进两个以上的功能，或者尝试一些不确定能不能成的改法时，就需要用到 Git 最核心的 **分支（Branch）** 机制。

### 1\. 主分支与并行开发

默认情况下，初始化好的 Git 仓库里只有一条 **主分支（通常叫 `main` ）** 。你可以把主分支想象成一棵树最粗的 **主树干** ，它是大家约定俗成的项目主要开发路线，我们通常会保持主分支上的代码随时都是稳定、可用的状态。

当我们要同时开发多个功能时，就可以从主树干上分出不同的树枝（也就是创建新分支）来独立开发：

![从主分支 main 派生出两条独立功能分支并行开发](https://book.oiloil.org/assets/articles/git-from-scratch/03-main-trunk-and-feature-branches-v1.svg)

从主分支 main 派生出两条独立功能分支并行开发

#### 为什么要分出不同分支来开发功能？

假设我们正在优化自己的个人网站（就像第三章 [《如何从 0 到 1 Vibe Coding 一个个人网站》](https://book.oiloil.org/articles/vibe-coding-website-from-scratch) 里做的那样），现在主分支上已经有了一版基础页面。接下来我们打算同时尝试两个新功能：

- **功能 A（联系我分支）** ：在页面底部增加一个「联系我」区域，并且在页面 **右上角的顶部导航栏** 里增加一个「联系我」跳转入口；
- **功能 B（深色模式分支）** ：给整个网站增加深色模式配色，并且在页面 **右上角的顶部导航栏** 里增加一个「浅色 / 深色主题切换按钮」。

如果我们直接在主分支上把这两个功能混在一起改，万一「深色模式」改到一半发现配色全乱了、想彻底放弃，你就很难把深色模式的代码单独摘出来，还会连累已经写好的「联系我」功能。

而用分支的做法非常干净：我们让两个功能都以当前主分支的稳定版本作为 **共同起点** ，派生出两条独立的分支去写。这样做最大的好处是—— **如果其中一个分支的功能改坏了、不想要了，只要把那条树枝砍掉（删除该分支）就好，完全不会污染主分支，也不会影响另一个功能的开发** 。

#### 用自然语言创建与切换分支

平时在实际操作时，你不需要去背 `git checkout -b` 或 `git switch` 命令，直接用自然语言告诉 AI 你想干什么即可。比如要开始写第一个功能时，直接说：

帮我基于主分支创建一个新的分支，用来开发「联系我」功能。

如果想从当前分支切回主分支，或者切去另一条分支，也只需要说：

帮我切换到主分支。

这里有一个细节需要注意：每个分支上的功能改好之后，记得先让 AI 提交（Commit）一版代码存档；而在开始写第二个功能之前，记得让 AI **基于主分支** 去创建第二个分支，这样两条功能分支才是从同一个起点并行长出来的。

### 2\. 合并代码与解决冲突

当我们在各自的分支上把功能开发并测试好之后，最终还是要把树枝上的成果合回到主树干上，这个操作就叫做 **合并（Merge）** 。而在多人或多分支并行修改同一个文件时，最常遇到的情况就是 **代码冲突（Conflict）** ：

![为什么修改同一处导航栏会触发合并冲突，以及如何让 AI Agent 自动保留两侧新功能](https://book.oiloil.org/assets/articles/git-from-scratch/04-merge-conflict-ai-resolve-v1.svg)

为什么修改同一处导航栏会触发合并冲突，以及如何让 AI Agent 自动保留两侧新功能

#### 第一个分支顺利合入主分支

接上面的例子，假设我们的「联系我」分支和「深色模式」分支都已经各自开发完毕并提交了版本。现在我们先把「联系我」功能合进主分支，直接跟 AI 说：

帮我把「联系我」这个分支合并到主分支。

因为这段时间主分支自己没有动过，所以这次合并会非常丝滑。合并完成之后，主分支这棵主树干就往上长高了一截（生成了一个带有「联系我」入口的新版本）。

#### 为什么合第二个分支时会出现冲突（Conflict）？

当主分支合并了「联系我」之后，主分支就有了新的版本，这时旁边的「深色模式」分支跟最新的主分支就 **不同步** 了。

而且看现在的页面，这两个分支 **都修改了同一处代码** ——也就是页面右上角的顶部导航栏（「联系我」分支在导航栏最右边加了联系入口，而「深色模式」分支也在导航栏同一个位置加了主题切换按钮），并且两边修改的内容不一样。

因为两个分支改了同一处代码且内容不同，Git 通过程序没法自动决定最后应该保留什么，就会暂停合并，提示出现了 **冲突（Conflict）** 。

#### 让 AI Agent 自动合并并解决冲突

在 AI Agent 时代，AI 能够很好地处理这类冲突，自动保留两边都有的新功能。

处理的方法是：我们先切换到还没合并的「深色模式」分支，把主分支最新的变更合并进来并处理掉冲突，最后再合回主分支。你可以直接跟 AI 说：

帮我切换到深色模式分支，合并一下主分支的最新变更，如果有冲突帮我处理一下，同时保留联系我入口和深色模式切换按钮。

等 AI 在「深色模式」分支里把冲突解决完、你也确认页面右上角两个按钮都能正常显示后，再跟 AI 说最后一句：

帮我切到主分支，并且合并深色模式分支的代码。

因为冲突已经在前一步解决干净了，这时候主分支就能毫无阻碍地合入深色模式，两个分支的功能就完整汇合到了主树干上。

## 推送到 GitHub 与页面导览

学会了在自己电脑本地做版本和分支管理之后，接下来我们看看怎么把本地写好的代码放到 GitHub 云端去，以及打开别人或自己的 GitHub 仓库页面时，上面的各个模块分别代表什么。

### 1\. 创建仓库与一键推送

要把本地代码传到 GitHub 上，既可以用传统的网页手动创建方式，也可以直接交给 AI Agent 全自动跑完。我先把传统流程里那几行大家经常看到的命令讲明白，再教大家现在最省事的 AI 做法：

![传统网页建库敲命令与让 AI Agent 通过 gh CLI 全自动创建推送的对比](https://book.oiloil.org/assets/articles/git-from-scratch/05-github-cli-push-workflow-v1.svg)

传统网页建库敲命令与让 AI Agent 通过 gh CLI 全自动创建推送的对比

#### 传统方式：网页新建仓库与那几行命令到底是什么意思？

如果按以前纯手动的方式，你登录 GitHub 网站后点击右上角的 `+` 号选择 `New repository` （新建仓库），表单里通常会让你填这几项：

![GitHub 网页新建仓库表单：填写名称、选择公开或私有、配置 README 与 .gitignore](https://book.oiloil.org/assets/articles/git-from-scratch/05b-github-new-repo-ui-v1.webp)

GitHub 网页新建仓库表单：填写名称、选择公开或私有、配置 README 与.gitignore

1. **Repository name（仓库名称）与 Description（描述）** ：一般用英文和短横线给项目起个名字（比如 `my-website` ）；
2. **Public（公开）还是 Private（私有）** ：选 `Public` 就是开源仓库，网上的任何人都能看到并下载你的代码；如果是自己写的商业项目或不想公开的代码，选 `Private` 闭源，就只有你自己和你邀请的协作者能看见；
3. **初始化配置项** ：
	- **`README.md`** ： `README` 的字面意思就是「读我」，它是一个 Markdown 格式的文档，相当于这个项目的说明书和门面（打开任何 GitHub 仓库主页，底下直接展示出来的那篇图文介绍就是 `README.md` ）；
		- **`.gitignore`** ：指定哪些文件不需要上传到 GitHub（下一节我们会详细讲）；
		- **`License` （开源许可证）** ：如果做开源项目，用来声明别人可以怎么合法使用你的代码（比如最宽松常用的 `MIT License` ）。

当你创建一个空仓库后，GitHub 页面上会列出一串终端命令。这四行命令在空仓库页面最常见，我们依次看下每一句的含义：

- `git commit -m "first commit"` ：把准备好的文件修改正式保存为一次提交记录（Git 底层会先用 `git add` 把要存档的文件放进「暂存区」待提交清单，再用 `commit` 正式存档；用 AI 操作时它会帮你把这两步一起做完）， `-m` 后面的引号里写的就是这次版本的文字说明；
- `git branch -M main` ：把当前所在的本地分支 **重命名** 为 `main` （注意这里的 `-M` 是强制改名的意思，不是切换分支）；
- `git remote add origin https://github.com/你的用户名/仓库名.git` ：给本地仓库添加一个云端远程仓库的地址，并把这个远程地址简称为 `origin` 。 **注意： `origin` 是云端远程仓库的代号，不是分支名字；而且执行完这一步只是在本地记下了云端地址，代码还没有真正上传上去** ；
- `git push -u origin main` ：真正把本地 `main` 分支上的代码 **推送（Push）** 上传到刚才起名为 `origin` 的云端仓库里。中间的 `-u` 参数意思是让本地的 `main` 分支和云端的 `main` 分支建立固定的绑定跟踪关系——绑定过这一次之后，以后你再想上传代码，只需要简写 `git push` 就可以了。

#### AI Agent 时代推荐做法：用连接器或 gh 命令行一键搞定

知道了上面那几行命令在干什么之后，平时我们自己做项目时， **完全不需要自己去开网页点表单、复制仓库链接和敲命令** 。

如果你用的 AI Agent（比如 Codex 等）内置了 GitHub 连接器（Connector），可以直接在设置里点一下授权连接；如果没配连接器，更通用的一招是让 AI 帮你装一个 GitHub 官方的命令行工具 **`gh`** 。你只需要跟 AI 说：

帮我安装一下 GitHub 的官方命令行工具 gh，并引导我登录授权。

AI 安装好 `gh` 之后，会自动在你的浏览器里弹出一个 GitHub 官方授权页面，你输入终端里给的验证码点一下确认，本地 AI 就拥有了操作你 GitHub 账号的权限。

授权完成之后（只需要做这一次），以后你任何时候写了一个新项目想传到 GitHub，直接跟 AI 说一句话就行：

帮我在 GitHub 上创建一个新的私有仓库，名字叫 my-portfolio，然后把我们现在的代码推上去。

AI 会在后台自动帮你创建好云端仓库、关联好远程地址，并把本地代码完整推送上去，全程只需要几秒钟。

#### 反向操作：怎么把别人的开源项目（或自己的云端仓库）下载到本地？

除了把我们自己写的代码推上 GitHub，平时大家最常遇到的另一个场景是：在网上看到别人开源了一个好用的项目或工具，或者自己换了一台新电脑，想把 GitHub 上的代码弄到本地电脑上跑起来。

很多新手打开别人的 GitHub 仓库时，看到右上角绿色的 `<> Code` 按钮点开有一个 `Download ZIP` （下载压缩包），就会直接点下载。其实 **更推荐的做法是让 AI 用 `git clone` （克隆）把仓库拉下来，而不是直接下载 ZIP 压缩包** ：

![GitHub 仓库右上角绿色 Code 按钮下拉菜单：优先复制 HTTPS 网址用 git clone 克隆](https://book.oiloil.org/assets/articles/git-from-scratch/05c-github-clone-vs-zip-ui-v1.webp)

GitHub 仓库右上角绿色 Code 按钮下拉菜单：优先复制 HTTPS 网址用 git clone 克隆

- **点 `Download ZIP` 的问题** ：下载下来的只是一个普通的静态文件夹，里面 **没有 `.git` 版本记录，也没有和原仓库的关联** 。如果过两天原作者修复了 Bug 或者更新了新功能，你没法一键升级，只能再去网页上重新下一次压缩包；
- **用 `git clone` （克隆）的好处** ：克隆会把整个项目的代码连同 `.git` 历史完整下载到本地，并且自动记住云端仓库的地址。

平时看到想试用的开源项目，直接把 GitHub 网址复制给 AI Agent 说一句：

帮我把这个 GitHub 仓库克隆到本地，并安装依赖跑起来：https://github.com/oil-oil/oil-git

等以后原作者更新了新版本，你只需要在这个项目目录里跟 AI 说一句（对应 `git pull` ）：

帮我拉取一下这个项目的最新更新。

AI 就会自动把原作者新增的代码同步到你电脑上，非常省心。

### 2\. 看懂 GitHub 仓库界面

当代码推送到 GitHub，或者我们平时去逛别人的开源项目时，面对满屏的英文按钮很容易眼花。其实整个 GitHub 仓库页面，你只需要认准 **顶部的核心标签栏** 和 **右上角与侧边栏的几个常用入口** 就够了（下面以真实的开源仓库页面为例）：

![真实的 GitHub 仓库界面导览：顶部标签栏、右上角常用操作与右侧 Releases 安装包下载区](https://book.oiloil.org/assets/articles/git-from-scratch/06-github-repo-interface-real-v1.webp)

真实的 GitHub 仓库界面导览：顶部标签栏、右上角常用操作与右侧 Releases 安装包下载区

#### 顶部三个核心标签栏：Code、Issues 与 Pull requests

1. **`Code` （代码主页）** ： 点进来默认看到的就是项目的文件夹列表，往下滚就是刚才说的 `README.md` 项目说明书。 这里有一个新手常问的细节：在文件列表左上角有一个分支切换下拉框（默认显示 `main` ）。你会发现 **云端看到的分支列表，有时候和你电脑本地的分支列表是不一样的** ——因为云端仓库和你的本地仓库本质上是两个独立的仓库，你在本地新建了一条分支，只要还没执行推送（Push），云端是不会凭空多出这条分支的。
2. **`Issues` （问题与需求讨论区）** ： 当你使用别人的开源软件遇到了报错 Bug，或者想提一个新功能建议时，就可以点进 `Issues` 页面，点击右上绿色的 `New issue` 发帖提问。 Issue 有两种状态：还没解决、正在讨论中的叫做 **`Open`** ；如果作者已经把这个 Bug 修好了，或者觉得这个问题不需要处理，就会把它关闭变成 **`Closed`** 。平时自己用开源项目踩坑报错时，去它的 `Issues` 里搜一下报错关键词，往往能在 `Closed` 列表里直接找到现成的解决办法。
3. **`Pull requests` （简称 PR · 拉取请求）** ： 用来审查和合并代码改动的地方，这是团队协作和规范开发最核心的功能，我们在紧接着的下一大节里单独展开讲。（紧挨着它的 **`Actions`** 则是 GitHub 的云端自动化流水线机房，用来在每次推代码时自动跑测试或自动打包软件。）

#### 右上角与侧边栏的常用概念：Releases、Pin、Watch、Fork、Star 与 Contributors

- **`Releases` （发行版 / 安装包下载区）** ：很多刚逛 GitHub 的朋友想安装某个开源桌面软件（比如前面提到的 Oil Git），打开仓库看到满屏都是 `src/` 、 `package.json` 等源码文件，不知道安装程序在哪下。其实只要看页面 **右侧边栏中间的 `Releases` 区域** ，点进去就能直接下载作者打包好的 Mac（`.dmg` ）或 Windows（`.exe` ）安装包。反过来，当我们自己的项目做好了一个重要大版本（比如 `v1.0.0` ），也可以让 AI 帮我们打一个版本标签（ `git tag` ）并发布到 `Releases` 里；
- **`Pin` （置顶到个人主页）** ：如果你在自己的 GitHub 账号下建了很多个仓库，可以在个人主页点 `Customize your pins` ，把最满意的最多 6 个代表作仓库固定（Pin）在个人主页最显眼的位置；
- **`Watch` （订阅通知）** ：点一下 `Watch` ，相当于订阅了这个仓库的动态，以后别人在这里提了新的 Issue、PR 或者发布了新版本，你都会收到通知；
- **`Fork` （派生 / 复制一份到自己名下）** ：当你看到一个很好的开源项目，想在它的代码基础上做二次开发改成自己的版本，但你又没有权限直接修改原作者的仓库，就可以点一下右上角的 `Fork` 。它会在 **你自己的 GitHub 账号下创建一个关联的同名仓库** 。你在自己 Fork 出来的仓库里怎么改都不会影响原作者；而当原作者的仓库更新了新功能时，你还能在页面上直接点击 `Sync fork` （同步），把原作者的更新一键拉回到你的仓库里；
- **`Star` （点星收藏）** ：相当于给这个项目点赞加收藏。在 GitHub 生态里， `Star` 数量代表了社区对这个项目的喜爱与认可程度；一个开源项目在短时间内拿到的 `Star` 越多，就越容易登上 GitHub 官方的 Trending（热门趋势榜），获得平台的自然推流；
- **`Contributors` （贡献者列表）** ：在仓库主页右侧边栏最下方，会展示所有给这个仓库成功提交并合入过代码的人的头像列表。

## Pull Request 审查与同步

很多自己一个人写项目的朋友会问：既然代码仓库是我自己的，我每次在分支上写完代码，直接在本地合进 `main` 再推上去不就行了，为什么还要去用 GitHub 上的 **Pull Request（简称 PR）** ？

### 1\. PR 原理与四个标签页

**Pull Request** 的字面意思是「拉取请求」。如果你给别人的开源项目贡献代码，因为不能直接往别人的主分支里合并代码，你需要先 Fork 一份仓库到自己名下并克隆到本地，切出新分支开发完后，再提一个 PR 请求仓库维护者拉取合并你的代码。

哪怕是我们自己一个人开发项目，把新功能推到云端提一个 PR，也是非常好的习惯——因为它能把「这一个功能到底改了哪些文件、自动化测试有没有跑通」集中展示在一个干净的审查页面里：

![真实的 GitHub Pull Request（PR）页面：四大标签页、Submit review 按钮与 Files changed 红绿逐行对比](https://book.oiloil.org/assets/articles/git-from-scratch/07-pull-request-real-ui-v1.webp)

真实的 GitHub Pull Request（PR）页面：四大标签页、Submit review 按钮与 Files changed 红绿逐行对比

点开任何一个 PR 页面，你会看到标题下方有四个标签页，它们各自的作用非常清晰：

1. **`Conversation` （讨论与时间线）** ： 这里首先展示创建这个 PR 时写的修改说明（改了什么、为什么要改），底下则是按时间顺序排列的评论区和每次提交的流水记录。团队成员或者 AI 代码审查机器人（Code Review Bot）写的整体反馈都会出现在这里。
2. **`Commits` （本次 PR 包含的提交记录）** ： 列出这条功能分支上一共做了哪几次 Commit 存档。这里有一个很实用的协作机制：当审查者看完你的 PR 提了条修改意见（比如「按钮颜色太淡了」），你 **不需要关掉这个 PR 重新提一个** ，只需要在本地同一个分支上改好代码，再做一次新的 Commit 并推送上去，这个新的 Commit 就会自动追加进当前的 PR 里。审查者点开 `Commits` 标签，只需要看你最新追加的那一次提交，就能确认问题修没修好，省去了把所有代码从头再看一遍的麻烦。
3. **`Checks` （自动化检查）** ： 正规的项目通常会在 GitHub 上配置自动化的流水线测试（比如检查代码类型有没有写错、能不能正常打包构建，以及验证单个功能模块的单元测试和模拟真实用户页面操作的端到端测试有没有通过）。每次你往 PR 里推代码，GitHub 就会自动在云端跑一遍这些检查，全部通过会亮绿勾（ `✓` ），报错则会亮红叉（ `✕` ）。在请真人看代码或者合并进主分支之前，先看一眼 `Checks` 有没有报错并让 AI 修好，能拦住绝大多数低级 Bug。
4. **`Files changed` （文件变更逐行对比）** ： 把这次分支相对于主分支 **所有新增（绿色高亮）和删除（红色高亮）的代码行** 并排列出来。审查代码时，可以把鼠标悬停在任意一行代码旁边点加号写评论，最后点击右上角的 `Review changes` → `Submit review` 提交审查意见（可以选择仅评论 `Comment` 、批准合并 `Approve` ，或者要求修改后再合 `Request changes` ）。

### 2\. 用 AI 跑通 PR 闭环

理解了 PR 的四个标签页之后，我们平时完全不用自己去网页上手填 PR 表单。下面我们用给个人网站增加「作品分类筛选」功能的真实场景，演示怎么用 5 句自然语言指挥 AI Agent 跑完从建分支、提 PR、按反馈增量修改，到云端合并并拉回本地的完整闭环：

![用自然语言指挥 AI Agent 完成新建分支、提 PR、按反馈增量更新、云端合并与拉回本地的五步闭环](https://book.oiloil.org/assets/articles/git-from-scratch/08-ai-pr-closed-loop-v1.svg)

用自然语言指挥 AI Agent 完成新建分支、提 PR、按反馈增量更新、云端合并与拉回本地的五步闭环

#### 第一步：新建分支并在本地开发预览

我们先让 AI 切出一个专门的功能分支把效果做出来看看：

新建一个作品筛选分支，给作品区增加「全部、AI 工具、网站」筛选按钮，先让我看看效果。

#### 第二步：提交推送到 GitHub 并创建 PR（先不合并）

在浏览器里看了一眼，筛选功能已经有了。接着我们让 AI 把这条新分支推上云端，并直接创建一个合并到 `main` 的 PR：

把这个功能提交并推送到 GitHub，创建合并到 main 的 PR，写清楚修改说明，先不要合并。

这里有一个细节可以验证你的理解：此时如果你让 AI 切回本地的 `main` 主分支刷新网页，你会发现页面上 **还没有** 筛选按钮——因为创建 PR 只是在云端「提出了合并申请」，代码还待在作品筛选分支上，并没有真正合进 `main` 。

#### 第三步：根据反馈修改代码，追加推送到同一个 PR

假设你在看预览或者看 PR 的时候，发现深色模式下选中按钮的高亮不够明显。这时候不需要新建分支，直接让 AI 在原分支上改好再推上去：

把筛选按钮选中的状态做得更明显一些，确认深色模式下也能看清，提交并推送到同一个分支。

推上去之后，你去刷新 GitHub 上刚才那个 PR 页面，就会看到 `Commits` 里自动多出了这第二次提交，PR 的变更内容也已经实时更新了。

#### 第四步：确认无误后在云端合并 PR

确认效果和检查都没问题了，你可以自己在 GitHub 网页上点绿色的 `Merge pull request` 按钮，或者直接跟 AI 说一句：

可以合并这个 PR 了。

#### 第五步（极易漏掉的一步）：切回本地主分支并拉取（Pull）最新代码

很多新手在云端合并完 PR 之后，转头回到自己电脑上继续基于 `main` 开发下一个功能，结果发现刚才写的筛选功能怎么不见了？

原因很简单： **刚才的合并（Merge）动作是发生在 GitHub 云端服务器上的** 。云端的 `main` 分支已经包含了最新的作品筛选代码，但你电脑本地的 `main` 分支还停留在合并前的旧状态。所以在云端合并完 PR 之后，一定要记得跟 AI 说最后这一句，把云端最新的代码 **拉取（Pull）** 回本地：

帮我切到本地主分支，并且从 GitHub 拉取一下最新的代码。

执行完这一步（对应 `git checkout main` 和 `git pull` ），你本地的主分支就和云端彻底同步到最新状态了。

## 日常开发的三个避坑实战

掌握了本地提交、分支合并与 GitHub PR 流程之后，你已经能应付绝大多数日常开发了。最后我把自己在用 AI Agent 写项目时最常遇到的三个高频场景和注意细节整理出来，帮大家避开日常开发里常见的问题。

### 1\. 敏感密钥与忽略清单

当我们把项目推送到 GitHub 云端时， **并不是项目文件夹里的所有东西都应该传上去的** 。有两类文件绝对不能直接推上云端：第一类是体积特别大的文件（比如几百兆的原片视频，或者安装框架时自动生成的几十万个第三方依赖文件 `node_modules` ）；第二类则是绝对不能泄露的敏感信息（比如你花钱充值的大模型 `API Key` 、数据库密码等）。

为了管好这些文件，我们需要配合使用 `.env` 、`.env.example` 和 `.gitignore` 这三个文件：

![使用 .env、.env.example 与 .gitignore 保护 API Key 密钥并隔离大文件](https://book.oiloil.org/assets/articles/git-from-scratch/09-env-and-gitignore-security-v1.svg)

使用.env、.env.example 与.gitignore 保护 API Key 密钥并隔离大文件

#### .env、.env.example 与.gitignore 怎么配合？

1. **在 `.env` 里存放真实的敏感密钥（只留本地，绝不上传）** ： 在项目根目录下创建一个名叫 `.env` （或 `.env.local` ）的环境变量配置文件，把你真实的 `OPENAI_API_KEY=sk-xxxx` 写在里面供本地程序读取；
2. **用 `.gitignore` 告诉 Git 忽略哪些文件** ： 在根目录下创建 `.gitignore` 文件，把 `.env` 、 `node_modules/` 、 `*.mp4` 等路径写进去。只要写进了 `.gitignore` ，Git 在做提交（Commit）和推送（Push）时就会直接无视这些文件，不会把它们传到 GitHub 上；
3. **用 `.env.example` 给协作者或未来的自己留一份「配置模板」** ： 既然 `.env` 被忽略不上传了，那别人把你的代码拉下来（或者你自己换了台新电脑拉下来），怎么知道这个项目需要配置哪些环境变量才能跑起来呢？ 做法是额外建一个 `.env.example` 文件一起提交到 GitHub 上。在这个文件里， **只写变量名和注释说明它的用途，不填写真实的密钥值** （例如写 `OPENAI_API_KEY=在这里填入你的OpenAI密钥` ）。别人拉下代码后，照着 `.env.example` 复制一份改名为 `.env` 并填上自己的 Key 就能跑了。

平时新建项目用到 API Key 时，可以直接这样交代 AI：

帮我把代码里的 API Key 抽离到.env 文件里，创建一份带注释说明的.env.example 模板，并确认.env 和 node\_modules 已经写进了.gitignore 忽略清单。

#### 两个必须留心的避坑细节

- **已经提交过的 `.env` ，事后加进 `.gitignore` 不会自动消失** ： 如果你一开始忘了配 `.gitignore` ，不小心把带着真实密钥的 `.env` 提交（Commit）甚至推送到了 GitHub 上，这时候你再把 `.env` 写进 `.gitignore` 是没用的——Git 依然会继续追踪它，而且之前的历史提交记录里别人照样能翻出你的 Key。一旦发生这种情况，第一件事是去平台后台把泄露的旧 Key 删掉换新，同时跟 AI 说：
	我之前不小心把.env 提交进 Git 了，帮我把它从 Git 的追踪记录中移除（保留我本地的.env 文件），并加入.gitignore。
	复制
- **项目部署上线时，要在服务器或部署平台上单独配环境变量** ： 因为 `.env` 只在你自己电脑本地、没有传上 GitHub，所以当你把 GitHub 仓库连到 Vercel、Railway 或自己的云服务器部署上线时，线上环境里是没有这个 `.env` 文件的。你需要在部署平台后台的 `Environment Variables` （环境变量）设置面板里，把这些 Key 单独填进去，线上网站才能正常调用接口。

### 2\. 用 Stash 临时保存修改

平时开发时经常会遇到这种情况：我们在某个分支上开发功能才写到一半，当前的代码还不值得单独提交（Commit）成一个版本，但写了一半的修改又不能直接舍弃；偏偏这时候我们需要先切换到另一个分支去处理别的问题。

这时候就可以用 Git 的 **`Stash` （临时保存）** 功能：

![代码改了一半需要切分支时，让 AI Agent 使用 Stash 临时保存并恢复修改](https://book.oiloil.org/assets/articles/git-from-scratch/10-git-stash-temp-drawer-v1.svg)

代码改了一半需要切分支时，让 AI Agent 使用 Stash 临时保存并恢复修改

`Stash` 的作用就是把当前还没写完的修改先临时收起来，让工作区回到上一次提交时的干净状态；等你切换到另一条分支处理完问题、再切回原分支之后，可以把刚才临时保存的修改恢复出来继续开发。

遇到这种场景时，直接跟 AI Agent 说：

我现在改了一半的代码还不想提交，先帮我用 stash 临时保存起来，然后切到主分支。

等另一个分支的事情处理完，再跟 AI 说：

帮我切回刚才的功能分支，把之前 stash 临时保存的修改恢复出来继续开发。

### 3\. 用 Worktree 多开并行

到了 AI Agent 时代，我们如果想让两个 Agent 同时开发两个功能，只在一个项目目录里来回切分支是很不方便的——因为同一个文件夹同一时刻只能处在一个分支上，两个 Agent 在同一个目录里改代码马上就会互相影响。

要让两个 Agent 同时并行开发，可以使用 Git 的 **`Worktree` （工作树）** ：

![使用 Git Worktree 将不同分支展开到独立文件夹，让两个 AI Agent 同时并行开发并补齐初始化环境](https://book.oiloil.org/assets/articles/git-from-scratch/11-git-worktree-parallel-agents-v1.svg)

使用 Git Worktree 将不同分支展开到独立文件夹，让两个 AI Agent 同时并行开发并补齐初始化环境

#### 区分「分支（Branch）」与「工作树（Worktree）」

我们可以这样区分这两个概念：

- **分支（Branch）** ：记录的是一条开发路线和提交历史；
- **工作树（Worktree）** ：则是把某个分支的代码展开到一个实际的文件夹里，供我们编辑、运行和测试。

默认情况下，我们的项目只有一个工作目录。而使用 `worktree` ，我们可以把不同分支放到不同的工作目录里同时保持打开—— **两个 Agent 各自在自己的目录里修改代码和提交版本，但底层共用的是同一套 Git 体系** 。

#### 重要避坑点：新 Worktree 不会自动复制.gitignore 里的文件

创建一个新的工作树（Worktree）之后，有一点需要特别注意： **写在 `.gitignore` 里被忽略的文件，是不会自动复制过去的** ——这和我们平时手动用 `Ctrl + C / Ctrl + V` 复制整个文件夹不一样。

比如体积很大的第三方依赖包文件夹 **`node_modules`** ，以及存放真实 `API Key` 的 **`.env` 配置文件** ，因为都在 `.gitignore` 的忽略清单里，新建的工作树目录里默认是没有它们的。

所以创建新工作树之后，我们需要重新安装一次依赖，并把 `.env` 配置补齐完成初始化。平时可以直接这样跟 AI 说：

帮我基于主分支创建一个新的 worktree 目录来开发「深色模式」，并把当前目录的.env 复制过去、安装好项目依赖，确保新目录能直接运行。

等 AI 创建并初始化好这个新目录后，你只需要新开一个 AI Agent 窗口进入这个新的 worktree 文件夹，就能让第二个 Agent 在里面同时开发「深色模式」了；等那边开发并合并完之后，再让 AI 帮你把临时创建的 worktree 目录清理掉即可。

## 总结

最后，我们用四点快速回顾一下这一章的核心内容：

1. **Git 与 GitHub 的分工** ：Git 是电脑本地的版本管理工具（像单机游戏的本地存档，写完阶段性功能就让 AI 做一次 `Commit` 提交，改坏了随时查状态或按历史记录撤回；刚开始学强烈建议搭配 **[Oil Git](https://git.oiloil.org/)** 可视化对照着看）；GitHub 则是云端代码托管与协作平台（像云端存档与多人联机大厅）。
2. **分支并行与冲突处理** ：主分支（ `main` ）是稳定的主树干，同时开发多个功能时从主分支派生独立分支，改坏了直接砍掉分支即可；当两个分支改了同一处代码引发冲突（Conflict）时，直接让 AI Agent 合并并自动保留两边的新功能。
3. **GitHub 推送、克隆与 PR 审查闭环** ：配置好 GitHub 连接器或让 AI 安装官方 `gh` 命令行工具后，一句话就能建库推送；下载别人的开源项目优先用 `git clone` 克隆（方便后续随时 `git pull` 拉取更新），找桌面软件安装包则看右侧边栏的 `Releases` ；开发新功能时养成提 **Pull Request（PR）** 的习惯，看懂 `Conversation` 、 `Commits` 、 `Checks` 、 `Files changed` 四个标签页，并在云端合并 PR 后记得让 AI 把最新代码拉取（Pull）回本地主分支。
4. **三个日常高频避坑** ：① 用 `.env` 存真实密钥、`.env.example` 留配置模板、`.gitignore` 排除大文件与密钥（注意已提交过的 `.env` 必须让 AI 从追踪记录中移除，线上部署需在服务器后台单独配环境变量）；② 代码改了一半急需切分支时用 `Stash` 临时收起；③ 让多个 Agent 同时开发不同分支时用 `Worktree` 展开到独立文件夹，并记得在新工作树里补齐 `.env` 和重新安装依赖。
